# SafeMeal Agent 项目功能与技术栈总结

> 项目定位：SafeMeal Agent 是一个面向菜谱与饮食安全场景的垂直领域智能 Agent 系统。系统以结构化菜谱数据为确定性底座，结合 Milvus 向量检索、LightRAG 跨文档检索、Neo4j 饮食安全图谱和多工具 Agent 编排，实现菜谱问答、个性化推荐、饮食约束过滤、文档知识入库、评测验收、监控告警和反馈闭环。

## 二、技术栈按大厂面试能力域分类

### 1. Agent 架构与工具调用编排

- 关键词：Planner / Executor / Observer / Reflector / Responder、多工具调用、工具注册表、工具预算、重复调用拦截、降级策略。
- 项目实现：
  - 将 Agent 运行拆成规划、执行、观察、反思、回答多个阶段。
  - 工具调用包含结构化菜谱工具、检索工具、图谱安全工具。
  - 对工具超时、部分失败、结果过大进行隔离和压缩，避免正确证据被失败工具覆盖。
- 技术栈评级：8/10
- 评价：实现已经超过普通 Demo，具备工程化 Agent 框架雏形；不足是路由准确率和工具选择准确率仍需通过评测继续优化。

### 2. RAG 检索链路与召回质量优化

- 关键词：Embedding、Milvus、Rerank、LightRAG、RRF 融合、context recall、Hit@5。
- 项目实现：
  - 支持文档向量化后写入 Milvus。
  - 支持 Rerank 对召回结果重排，失败时保留原始结果而不是清空。
  - 支持 LightRAG 跨文档关系检索。
  - 多路检索结果使用 RRF 融合。
- 技术栈评级：7/10
- 评价：链路完整且具备真实工程问题处理，例如重排失败降级；但评测指标显示召回质量仍有提升空间。

### 3. 垂直领域知识图谱与确定性安全规则

- 关键词：Neo4j、图查询、结构化食材、安全字段、忌口/过敏过滤、LLM 与规则边界。
- 项目实现：
  - 使用 Neo4j 管理菜谱、食材和饮食安全关系。
  - 对图数据进行结构化字段补齐，降低 `unknown` 返回。
  - 对过敏、忌口等高风险场景使用确定性规则，而不是完全交给 LLM。
- 技术栈评级：8/10
- 评价：这是项目最适合面试展示的亮点之一，能体现“LLM 不负责安全判断，规则和图谱负责硬约束”的工程意识。

### 4. LLM 工程与模型高可用

- 关键词：Provider Router、DeepSeek V4 Pro 备用模型、熔断器、首包检测、流式输出、结构化输出修复。
- 项目实现：
  - 主模型失败时可切换到备用模型。
  - 支持熔断和恢复窗口。
  - 流式输出场景避免主模型已经输出内容后再拼接备用模型答案。
  - 对结构化输出增加校验重试或修复机制。
- 技术栈评级：7/10
- 评价：比简单调用大模型更接近真实线上系统；但真实稳定性仍依赖长期压测和供应商异常场景覆盖。

### 5. 后端接口设计与业务分层

- 关键词：FastAPI、路由分层、Use Case、Port/Adapter、Repository、Pydantic Schema、鉴权中间件。
- 项目实现：
  - 后端按 `interfaces / application / infrastructure / domain / shared` 分层。
  - API 覆盖聊天、流式聊天、会话、记忆、知识库、上传、反馈、观测等模块。
  - 使用 trusted gateway 模式处理身份与权限。
- 技术栈评级：8/10
- 评价：分层清晰，接口边界较规范；项目已经有真实的工程复杂度，不是脚本式 Demo。

### 6. 数据持久化、迁移和一致性

- 关键词：MySQL、SQLAlchemy、Alembic、Repository、迁移门禁、数据初始化。
- 项目实现：
  - MySQL 存储菜谱、会话、消息、记忆、反馈等核心数据。
  - Alembic 管理数据库迁移。
  - 全新 volume 可自动初始化 schema 和种子数据。
  - 对旧库迁移提供备份校验和迁移门禁。
- 技术栈评级：8/10
- 评价：有明显后端工程意识，尤其是没有用 `stamp head` 掩盖旧库差异这一点适合面试展开。

### 7. 文档解析与知识入库流水线

- 关键词：Tika、多格式解析、分块策略、来源同步、校验和、增量更新、删除同步。
- 项目实现：
  - 支持 TXT、Markdown、JSON、CSV、HTML、PDF、DOCX、PPTX、XLSX 原生解析。
  - Tika 作为旧版 Office、扫描 PDF、RTF、ODF、EPUB 等场景的兜底。
  - 支持本地、HTTP、S3、飞书来源配置。
  - 支持定时同步、校验和去重、源文件删除同步。
- 技术栈评级：7/10
- 评价：系统设计完整，但部分外部来源需要真实环境验证，面试时应表述为“支持接入与测试覆盖”，不要夸大为“大规模生产稳定运行”。

### 8. 并发、限流与成本治理

- 关键词：Redis Token Bucket、FIFO 队列、租约、超时、Token 预算、成本预算。
- 项目实现：
  - HTTP、模型和工具调用可通过 Redis 做跨进程限流。
  - Agent 请求进入分布式 FIFO 队列，租约超时避免异常退出导致永久占用。
  - 对模型输出、上下文、总 Token、成本进行预算控制。
- 技术栈评级：8/10
- 评价：很适合互联网后端面试，因为它把 Agent 项目从“能跑”推进到“能控成本、能保护系统”。

### 9. 可观测性与线上治理

- 关键词：Prometheus、Grafana、Alertmanager、Trace、P95、错误率、成本指标。
- 项目实现：
  - `/metrics` 暴露 HTTP、Agent、模型、工具、Token、成本、限流、队列和熔断指标。
  - Prometheus 采集，Grafana 展示，Alertmanager 告警。
  - Agent Trace 持久化并支持 internal 角色查询。
- 技术栈评级：8/10
- 评价：监控闭环完整，是项目区别于普通课程项目的重要加分项。

### 10. 前端工程与接口联调

- 关键词：React、Vite、SSE、fetch 封装、状态管理、鉴权配置、调试控制台。
- 项目实现：
  - 支持普通聊天和 SSE 流式输出。
  - 支持历史读取、清空、反馈提交。
  - 支持配置 API 地址、用户编号、网关密钥和角色。
- 技术栈评级：7/10
- 评价：前端满足项目演示和联调用途；如果投前端岗位还需补充组件化、路由、状态管理、体验细节和自动化测试。

### 11. 评测体系与质量门禁

- 关键词：冻结数据集、LLM Judge、Top-1、Hit@5、faithfulness、answer correctness、regression gate。
- 项目实现：
  - 建立 58 条冻结数据集。
  - 支持 Judge 报告、门禁判断和基线回归。
  - 当前候选相对基线多项改善，但质量门禁未全过。
- 技术栈评级：不评级
- 原因：评测工程已实现，但指标没有全部达标。面试时应该诚实说明“我搭建了评测体系，并用它发现了召回、路由和安全红线问题”，而不是说“评测全部通过”。

## 三、项目亮点

1. 不把 LLM 当万能黑盒：饮食安全、过敏、忌口等硬约束由领域规则和 Neo4j 图谱兜底。
2. Agent 具备工程化运行闭环：路由、工具调用、失败降级、上下文压缩、结构化输出修复、Trace 记录。
3. RAG 不止向量搜索：同时有 Milvus、Rerank、LightRAG 和 RRF 融合。
4. 具备真实线上治理意识：限流、队列、熔断、成本预算、Prometheus、Grafana、Alertmanager。
5. 建立了评测门禁：虽然未全部通过，但能够量化问题，体现工程迭代能力。

## 四、当前仍需诚实说明的问题

1. 评测质量门禁未全过，不能声称 Top-1、Hit@5、工具选择、安全红线、P95 全部达标。
2. 前端是控制台性质，主要用于演示和调试，不是完整 C 端产品页面。
3. S3、飞书等外部来源接入需要真实账号和环境进一步验证。
4. 检索召回和 direct/refusal/clarification 路由仍有优化空间。
5. 安全红线仍需进一步收紧，尤其是饮食安全相关 false safety/usefulness 问题。
