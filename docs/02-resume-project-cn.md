# 简历项目介绍：SafeMeal Agent（食安智膳）智能饮食系统

## 推荐简历写法

### SafeMeal Agent（食安智膳）智能饮食系统

个人项目 / 后端与 Agent 工程  
技术栈：FastAPI、SQLAlchemy、MySQL、Redis、Milvus、Neo4j、LightRAG、Rerank、Prometheus、Grafana、Alertmanager、React、Vite、Docker Compose、Alembic、Pytest

- 设计并实现面向菜谱与饮食安全场景的垂直领域智能 Agent 系统，支持菜谱问答、个性化推荐、过敏/忌口安全过滤、知识库检索增强、文档入库、用户反馈和运行观测。
- 将 Agent 运行链路拆分为规划、执行、观察、反思和回答阶段，接入结构化菜谱工具、Milvus 向量检索、LightRAG 跨文档检索和 Neo4j 饮食安全图谱；通过工具预算、重复调用拦截、超时隔离和降级策略提升复杂问答稳定性。
- 构建 Embedding → Milvus → Rerank 的检索链路，并融合 LightRAG 检索结果；实现 Rerank 失败时保留原始召回结果，避免因重排异常导致知识库证据被清空。
- 基于 Neo4j 和确定性领域规则实现饮食安全过滤，将过敏、忌口、禁忌组合等高风险判断从 LLM 生成中剥离，降低幻觉和不安全推荐风险。
- 实现模型路由、DeepSeek V4 Pro 备用模型、熔断器和 SSE 首包检测；处理流式输出中途故障切换导致的答案拼接问题，避免主备模型输出混杂。
- 设计文档入库流水线，支持本地、HTTP、S3、飞书等来源，结合原生解析与 Apache Tika 兜底，完成自动分块、向量化、入库、定时同步和删除同步。
- 建立 Redis 分布式限流与 FIFO 并发队列，结合 Agent 迭代次数、工具调用数、上下文 Token 和模型成本预算控制，提升系统在高并发和长链路调用下的可控性。
- 接入 Prometheus、Grafana、Alertmanager 和 Agent Trace，暴露 HTTP、模型、工具、Token、成本、队列、熔断、P95 延迟等指标，支持问题定位和运行状态观测。
- 搭建 58 条冻结评测集、LLM Judge、质量门禁和基线回归流程；当前回答正确性、忠实度、错误率和 Token 成本已达标，但 Top-1、Hit@5、安全红线和 P95 延迟仍需继续优化。
- 实现 React/Vite 前端控制台，支持 SSE 流式聊天、历史记录、反馈提交、接口地址、用户身份、网关密钥和角色配置，完成前后端真实闭环联调。

## 精简版简历写法

### SafeMeal Agent（食安智膳）智能饮食系统

- 独立实现菜谱领域智能 Agent，支持菜谱问答、饮食安全过滤、知识库检索增强、文档入库、反馈闭环和运行监控。
- 设计 Planner/Executor/Observer/Reflector/Responder 多阶段 Agent 链路，接入 MySQL 菜谱工具、Milvus 向量检索、LightRAG 跨文档检索和 Neo4j 饮食安全图谱。
- 实现模型路由、备用模型故障切换、熔断器、SSE 首包检测、结构化输出修复、工具超时隔离和上下文压缩，提升 Agent 运行稳定性。

## 面试中推荐强调的项目价值

1. 这是一个“工程化 Agent 项目”，不是只调用一次大模型 API。
2. 饮食安全高风险判断由 Neo4j 和确定性规则处理，LLM 只做语言理解、规划和生成。
3. 检索链路不是单一向量库，而是 Milvus、Rerank、LightRAG 和 RRF 融合。
4. 项目有线上治理能力：限流、队列、熔断、成本、监控、Trace、告警。
5. 项目有评测闭环，并且诚实保留未达标指标，体现真实迭代意识。

## 面试中不要夸大的点

- 不要说“评测指标全部达标”。正确说法是：已搭建完整评测体系，回答正确性、忠实度、错误率、Token 成本等部分指标已达标，但 Top-1、Hit@5、安全红线和 P95 延迟仍需要继续优化。
- 不要说“前端是完整产品级应用”。正确说法是：前端是用于演示和联调的控制台，支持完整聊天闭环和 SSE 流式输出。
- 不要说“S3/飞书已经在线上大规模稳定运行”。正确说法是：代码层面支持多来源接入，真实外部环境需要凭证和长期运行验证。

## 30 秒口头介绍

SafeMeal Agent 是我做的一个垂直领域智能饮食 Agent。它不是简单的大模型聊天，而是把菜谱结构化数据、Milvus 向量检索、LightRAG 文档检索和 Neo4j 饮食安全图谱结合起来，让 Agent 可以在回答菜谱问题时调用工具、检索证据，并对过敏和忌口做确定性安全过滤。工程上我还做了模型路由、备用模型故障切换、熔断、SSE 流式输出、Redis 限流队列、Token 成本控制、Prometheus 监控和评测门禁。这个项目目前功能闭环可用，测试和基础接口通过，但评测上仍有召回、路由、安全红线和 P95 延迟等指标需要继续优化。

## 2 分钟口头介绍

SafeMeal Agent 是一个面向菜谱和饮食安全场景的垂类 Agent 项目，目标是让用户可以通过自然语言获得菜谱推荐、饮食限制过滤和知识库问答。系统后端采用模块化分层设计，接口层使用 FastAPI，业务层拆分为聊天、Agent、知识库、上传、记忆、反馈和观测模块，基础设施层接入 MySQL、Redis、Milvus、Neo4j、LightRAG 和模型 Provider。

Agent 运行时被拆成规划、执行、观察、反思和回答多个节点。规划阶段判断问题应该走结构化菜谱工具、知识库检索、图谱安全查询还是普通回答；执行阶段调用 MySQL 菜谱工具、Milvus 向量检索、LightRAG 跨文档检索和 Neo4j 饮食安全图谱；观察阶段对工具结果做压缩、去重和证据融合；回答阶段做结构化输出校验和 SSE 流式返回。为了提高稳定性，我实现了工具超时隔离、Rerank 失败降级、重复工具调用拦截、模型备用路由和熔断机制。

饮食安全是这个项目的重点。我没有把过敏和忌口判断完全交给 LLM，而是用 Neo4j 图谱和确定性领域规则进行硬约束过滤，LLM 主要负责理解用户意图、规划调用和组织语言。这样可以降低幻觉导致的不安全推荐风险。

工程治理方面，项目使用 Redis 做限流和分布式 FIFO 队列，用 Token 和成本预算限制 Agent 单次运行消耗；通过 Prometheus、Grafana、Alertmanager 和 Agent Trace 记录 HTTP、模型、工具、队列、成本、P95 延迟和错误率等指标。最后我还搭建了 58 条冻结评测集、LLM Judge、质量门禁和基线回归，能够量化 Top-1、Hit@5、正确性、忠实度、安全红线、延迟和 Token 消耗。当前项目功能闭环可用，测试通过，但评测门禁还没有完全通过，这也为后续优化提供了明确方向。
