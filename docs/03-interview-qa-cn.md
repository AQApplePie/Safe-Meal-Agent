# SafeMeal Agent 项目面试问题与参考答案

## 一、项目整体设计

### 1. 这个项目和普通大模型聊天 Demo 的区别是什么？

普通聊天 Demo 通常只是把用户问题直接转发给模型，然后返回模型文本。SafeMeal Agent 更接近一个工程化 Agent 系统：它有业务数据库、知识库、图谱安全规则、多工具调用、模型路由、故障切换、限流、监控、评测和反馈闭环。LLM 不是唯一决策来源，饮食安全和菜谱数据尽量由结构化工具和确定性规则提供。

### 2. 为什么选择菜谱和饮食安全作为 Agent 场景？

这个场景同时具备自然语言交互、结构化查询、知识检索和安全约束四类需求。比如用户可能问“我花生过敏，推荐一道快手晚餐”，系统既要理解意图，又要检索菜谱，还要检查过敏和忌口，最后生成自然语言答案。因此它适合验证 Agent 多工具编排和 RAG 的工程能力。

### 3. 系统整体链路是什么？

用户在 React/Vite 前端输入问题，前端携带用户身份、角色和网关密钥请求 FastAPI。后端完成鉴权、限流、会话处理后进入 Agent 链路。Agent 先规划路由，再调用 MySQL 菜谱工具、Milvus 检索、LightRAG 检索或 Neo4j 安全图谱，随后压缩和融合证据，最后调用模型生成结构化回答，并通过普通 JSON 或 SSE 流式返回。运行过程中的 Trace、指标和反馈会进入观测与评测闭环。

### 4. 项目最大的亮点是什么？

我认为最大的亮点是把 LLM、结构化业务工具、向量检索和知识图谱组合起来，并且明确了它们的职责边界。尤其是饮食安全这种高风险判断，不完全交给 LLM，而是通过 Neo4j 和确定性规则做硬约束过滤。

## 二、后端工程与接口设计

### 5. 后端为什么采用分层结构？

项目按 `interfaces / application / domain / infrastructure / shared` 分层。接口层负责 HTTP 入参出参和鉴权，应用层负责用例编排，领域层负责菜谱、安全等业务规则，基础设施层负责数据库、Redis、Milvus、Neo4j、模型等外部系统适配。这样可以降低模块耦合，让业务逻辑不直接依赖具体数据库或三方服务。

### 6. FastAPI 在项目里主要承担什么？

FastAPI 负责暴露后端 HTTP API，包括聊天、流式聊天、会话、记忆、知识库、上传、反馈、观测和管理接口。同时它结合 Pydantic 做请求和响应校验，结合依赖注入接入业务服务、鉴权上下文和运行时配置。

### 7. trusted gateway 鉴权模式是什么？

项目假设生产环境前面有可信网关，网关完成真实用户认证后，把用户编号、角色和网关密钥注入请求头。后端只信任带有正确 `X-SafeMeal-Gateway-Secret` 的请求，再读取用户和角色信息。这样可以把用户登录体系和业务 API 解耦。

### 8. 为什么还要做角色控制？

聊天可以对普通用户开放，但知识库管理、观测 Trace、内部集成状态等接口不应该给普通用户访问。项目通过角色区分 user、admin、internal 等权限，降低敏感数据和运维接口暴露风险。

### 9. 会话创建 500 的问题是怎么修复的？

问题原因是 SQLAlchemy 对象提交后，`created_at` 和 `updated_at` 依赖数据库默认值，session 关闭后 Pydantic 序列化触发懒加载，导致对象游离错误。修复方式是在创建实体时由应用显式写入 UTC 时间戳，避免提交后再访问未加载字段。

### 10. Repository 模式在项目里有什么价值？

Repository 隔离了业务用例和数据库实现。业务层只依赖端口，不关心底层是 SQLAlchemy、MySQL 还是测试替身。这样便于测试，也便于未来替换存储或拆服务。

## 三、Agent 架构与工具调用

### 11. Agent 为什么拆成规划、执行、观察、反思、回答多个节点？

拆分后每个阶段职责更清楚。规划器负责决定调用哪些工具；执行器负责运行工具并处理超时；观察器负责压缩、去重和融合结果；反思器负责判断是否需要补充调用；回答器负责生成最终答案。这样比一个大 Prompt 更容易调试、记录 Trace 和控制失败范围。

### 12. 工具调用如何避免无限循环？

项目通过三类限制避免循环：第一是限制 Agent 最大迭代次数；第二是限制工具总调用数；第三是拦截相同工具和相同参数的重复调用。如果模型反复提出相同工具调用，系统会直接阻断并进入降级或回答阶段。

### 13. 如果一个工具成功、另一个工具超时，系统怎么处理？

之前的问题是附加工具超时可能拖垮已有正确证据。现在的策略是保留成功工具的结果，把失败工具标记为 degraded，并在回答时基于已有证据返回，而不是统一失败。这符合 Agent 工程里的 partial success 思路。

### 14. 为什么要限制工具返回和上下文体积？

Agent 工具结果很容易变大，导致模型上下文膨胀、Token 成本升高、延迟变长，甚至让模型忽略关键证据。项目会对工具结果做裁剪、摘要和字段过滤，只保留回答所需的关键证据。

### 15. 什么是 KB-only 路由？

KB-only 指明确应该走知识库检索的问题，比如文档制度、资料内容、知识库事实。项目增加了路由守卫，避免这类问题不检索或误调用菜谱工具。评测显示 KB-only 路由有明显改善，但召回质量仍需优化。

## 四、RAG 与检索链路

### 16. 项目的 RAG 链路是什么？

项目的主检索链路是文档解析后分块，调用 Embedding 模型生成向量，写入 Milvus；查询时对问题向量化，从 Milvus 召回候选，再通过 Rerank 排序。同时系统还接入 LightRAG 做跨文档关系检索，并用 RRF 融合多路结果。

### 17. 为什么 Milvus 后还要 Rerank？

向量检索适合粗召回，但相似度不一定等于最终相关性。Rerank 会对 query 和候选文本做更细粒度匹配，提高排序质量。尤其在文档片段相似但答案点很细时，Rerank 能帮助把更相关的证据排到前面。

### 18. Rerank 失败时为什么不能直接返回空？

因为 Rerank 是排序增强，不是唯一证据来源。如果 Milvus 已经召回了候选，Rerank 失败时应该退回原始召回结果。否则一个增强模块异常会把可用证据全部清空，导致答案质量和稳定性下降。

### 19. LightRAG 在项目里解决什么问题？

LightRAG 用于跨文档关系检索。普通向量检索更偏局部片段匹配，而 LightRAG 可以补充文档之间的实体、关系和上下文线索。项目将 LightRAG 和 Milvus 的结果融合，提高复杂知识库问题的覆盖面。

### 20. RRF 融合是什么？

RRF 是 Reciprocal Rank Fusion，用于融合多个检索器的排序结果。它不依赖不同检索器的原始分数可比，而是根据排名位置给分，能比较稳健地融合 Milvus、Rerank、LightRAG 等多路结果。

### 21. 当前检索指标为什么还没达标？

主要原因是 KB-only 虽然路由改善了，但部分问题检索命中后没有正确暴露 source 或缺少金标关键词；另外召回语料规模和分块策略仍有调参空间。因此 Hit@5、context recall 等指标还没有达到目标。

## 五、知识图谱与饮食安全

### 22. 为什么饮食安全不用纯 LLM 判断？

过敏、忌口和禁忌组合属于高风险约束，LLM 可能幻觉或遗漏。项目把这类判断交给 Neo4j 图谱和确定性规则，LLM 只负责理解意图和组织答案。这样可以降低不安全推荐风险。

### 23. Neo4j 图谱里主要有哪些信息？

主要包括菜谱、食材、结构化食材字段、安全字段、忌口/过敏相关关系等。系统可以根据用户的饮食限制查询安全菜谱，也可以过滤不满足条件的候选。

### 24. 之前为什么会返回 unknown？

原因是部分图谱节点缺少结构化食材或安全字段，查询代码虽然存在，但数据闭环不完整。后续通过幂等迁移和字段补齐，把能从受控源数据证明的信息写回图谱；无法证明的仍保留 unknown，避免伪造确定性。

### 25. 如果用户说“我花生过敏”，系统怎么保证推荐安全？

系统会先抽取用户约束，将花生过敏写入当前上下文或记忆，然后在推荐阶段调用饮食安全过滤逻辑。候选菜谱会根据结构化食材和图谱安全关系过滤，最终答案中应避免推荐包含花生或相关风险食材的菜品。

## 六、模型路由与高可用

### 26. 为什么要配置备用模型？

模型服务可能超时、限流、连接失败或返回 5xx。备用模型可以提高系统可用性，避免主模型异常时整个 Agent 不可用。项目中备用模型配置为 DeepSeek V4 Pro。

### 27. 什么情况下会触发故障切换？

通常在主模型连接失败、超时、限流、服务端错误，且当前请求还没有产生正文输出时触发。如果主模型已经开始输出正文，系统不会再切换到备用模型拼接答案，而是终止或降级，避免用户看到两套模型混杂的内容。

### 28. 为什么流式输出中途切换很危险？

因为 SSE 是边生成边返回。如果主模型已经输出一半，突然切到备用模型继续生成，会造成风格、上下文和内容不一致，甚至拼接出矛盾答案。因此项目设计为：首包前失败可以切换，正文开始后不做主备拼接。

### 29. 熔断器解决什么问题？

熔断器用于避免持续调用已经异常的模型 Provider。当失败次数达到阈值后，短时间内直接绕过该 Provider，等恢复窗口后再试探性恢复。这样可以减少请求堆积和无效重试。

### 30. 结构化输出校验修复机制是什么？

模型有时会输出不符合 schema 的 JSON 或工具调用参数。项目会对结构化输出做校验，失败时尝试修复或重试，降低因为格式问题导致 Agent 崩溃的概率。

## 七、并发、限流与成本控制

### 31. 为什么 Agent 系统特别需要限流？

Agent 单次请求可能调用多个模型和工具，成本和耗时都比普通接口高。如果不限流，高并发下容易拖垮数据库、向量库、模型额度和后端线程。因此项目引入 Redis Token Bucket 和分布式 FIFO 队列。

### 32. Redis FIFO 队列为什么需要租约？

如果请求进入队列后进程崩溃，没有租约就可能永久占用并发名额。租约带过期时间，异常退出后名额可以自动释放，避免队列卡死。

### 33. Token 预算如何降低成本？

项目限制历史消息扫描数量、上下文 Token、模型最大输出、Agent 总 Token 和总成本。如果超出预算，就停止后续付费调用或压缩上下文，避免一次复杂请求无限消耗。

### 34. 为什么要记录模型价格？

只有记录不同模型的输入、输出和缓存输入价格，才能估算每次 Agent 调用成本，并做成本上限控制。项目通过配置注入价格，而不是写死在代码里，方便模型价格变化时更新。

## 八、可观测性与监控

### 35. 项目监控了哪些指标？

项目通过 `/metrics` 暴露 HTTP 请求、Agent 成功率和延迟、模型调用次数和耗时、工具调用次数和耗时、Token、成本、限流、队列深度、熔断状态、反馈和 Trace 持久化等指标。

### 36. Prometheus、Grafana、Alertmanager 分别做什么？

Prometheus 负责采集和存储指标，Grafana 负责展示 Dashboard，Alertmanager 负责接收 Prometheus 告警并做通知分发。项目还提供了通知接收器，把 firing/resolved 事件可靠写入本地 jsonl。

### 37. Agent Trace 记录什么？

Trace 记录 request、run、session 关联信息，Agent 节点运行过程，规划和反思理由，模型和工具调用，耗时、Token、成本和错误。它用于排查为什么 Agent 调错工具、为什么超时、为什么答案不符合预期。

### 38. P95 延迟为什么比平均延迟更重要？

平均延迟容易被大多数正常请求掩盖，而 P95 能反映长尾请求体验。Agent 系统经常受模型慢响应、工具超时、检索抖动影响，所以 P95 是判断线上稳定性的关键指标。

## 九、评测体系

### 39. 为什么要做冻结评测集？

如果没有固定数据集，每次改 Prompt 或工具策略都只能靠主观试用判断好坏。冻结评测集可以让不同版本在同一批问题上对比，量化 Top-1、Hit@5、正确性、忠实度、安全红线和延迟等指标。

### 40. LLM Judge 有什么风险？

LLM Judge 本身也可能不稳定、偏好某种表达或误判。因此项目既看 Judge 分数，也看确定性指标，比如路由命中、工具调用、错误率、Token、P95 和安全违规率。高风险样本还需要人工抽查。

### 41. 当前评测哪些指标达标？

根据验收摘要，回答正确性、faithfulness、Judge 覆盖率、错误率、错误答案率和平均 Token 消耗已经达到对应门槛。

### 42. 当前评测哪些指标未达标？

Route Top-1、Retrieval Hit@5、Context recall、工具决策/选择/参数准确率、工具结果利用率、安全违规率和 P95 延迟等仍未全部达标。因此不能说完整评测质量门禁已经通过。

### 43. 为什么面试时反而可以讲未达标指标？

因为真实工程不是所有指标一次性达标。能搭建评测体系、定位未达标原因、说明下一步优化方向，比只展示一个无法验证的 Demo 更有说服力。它体现的是工程迭代能力和诚实的质量意识。

### 44. 下一步会如何优化评测指标？

我会从四个方向优化：第一，继续改进 KB-only 路由和拒答/澄清问题识别；第二，调优文档分块、召回数量、Rerank 和 RRF 权重；第三，强化饮食安全规则和拒答模板；第四，对长尾工具调用做更激进的超时和快速失败。

## 十、前端与 SSE

### 45. 前端主要实现了什么？

前端是一个 React/Vite 控制台，支持 API 地址配置、用户身份、网关密钥、角色、SSE 流式聊天、历史读取、清空会话和反馈提交。它主要用于演示和联调完整闭环。

### 46. SSE 相比普通 HTTP 有什么优势？

SSE 可以让模型生成内容时边生成边返回，用户能更早看到首包，体验更接近实时聊天。对 Agent 来说，也可以把降级事件、首包超时事件、最终答案等分阶段返回给前端。

### 47. SSE 首包检测解决什么问题？

首包检测用于发现模型迟迟没有开始输出的情况。如果首包超时，系统可以触发降级事件或切换备用模型，避免用户长时间无反馈。

### 48. 前端为什么要配置网关密钥和角色？

因为项目默认是 trusted gateway 鉴权模式。为了本地演示和联调，前端控制台需要允许填写网关密钥和角色，并在请求头中携带这些字段，否则受保护接口会返回 401。

## 十一、文档入库与数据同步

### 49. 文档入库流水线包括哪些步骤？

包括来源抓取、文件解析、分块、Embedding、向量库入库和状态记录。来源可以是本地、HTTP、S3 或飞书；解析可以走原生解析或 Tika 兜底；分块支持递归、语义和自动策略。

### 50. 为什么要做增量同步和删除同步？

知识库需要和源文档保持一致。如果文件内容没变，重复入库会浪费成本；如果源文件删除，向量库里还保留旧内容会产生脏答案。因此项目用校验和跳过未变化文档，并支持源文件删除时同步删除分块。

### 51. Apache Tika 在项目中起什么作用？

Tika 是文档解析兜底组件。对于旧版 Office、RTF、ODF、EPUB、扫描 PDF 或原生解析失败的文件，可以用 Tika 尝试提取文本，提高文档来源兼容性。

## 十二、数据库与迁移

### 52. MySQL 在项目中存储什么？

MySQL 存储结构化菜谱、聊天会话、聊天消息、用户记忆、反馈等核心业务数据。菜谱表是结构化工具查询的基础。

### 53. Alembic 在项目中解决什么问题？

Alembic 管理数据库 schema 迁移，确保代码版本和数据库结构一致。项目还做了迁移门禁，避免在旧库 schema 不一致时直接 stamp head 掩盖问题。

### 54. 为什么不能随便删除生产 volume？

生产 volume 里可能有真实用户数据、反馈、会话和知识库状态。删除 volume 会造成数据丢失。项目要求旧库迁移前先做仓库外备份和 SHA-256 校验。

## 十三、项目不足与改进

### 55. 这个项目现在最大的不足是什么？

最大不足是完整评测门禁仍未通过，尤其是检索召回、工具选择、安全红线和 P95 延迟。功能链路可用，但质量指标还需要继续迭代。

### 56. 如果继续做，你会优先优化什么？

我会优先优化安全红线和长尾延迟。安全红线直接影响用户风险，必须优先收紧；长尾延迟影响用户体验和资源占用，需要通过工具快速失败、并发隔离和候选裁剪解决。之后再优化召回质量和路由准确率。

### 57. 这个项目适合投什么岗位？

最适合投后端开发实习、Agent 应用开发实习、AI 应用工程实习、RAG 工程实习。如果投纯前端岗位，前端部分还需要补产品化页面、组件体系和前端测试。

### 58. 面试官问“你项目里最难的问题是什么”，怎么回答？

可以回答：最难的是让 Agent 从“能回答”变成“稳定、可观测、可评测”。具体包括工具部分失败时如何保留正确证据，模型流式输出中如何处理故障切换，RAG 召回质量如何量化，饮食安全如何避免完全依赖 LLM，以及如何用限流、成本和监控保护系统。

### 59. 面试官问“你怎么证明项目有效”，怎么回答？

我会从三层证明。第一，功能层面：接口烟测、前端聊天闭环和 Docker 服务可运行。第二，工程层面：Ruff 和 Pytest 通过，监控和 Trace 可用。第三，质量层面：用 58 条冻结评测集和 LLM Judge 生成指标报告，同时保留未达标项，说明系统有效但仍有优化空间。

### 60. 面试官问“如果上线，你还缺什么”，怎么回答？

上线前还需要更严格的安全评测、压测、灰度发布、日志脱敏、密钥管理、用户权限系统、数据备份恢复、更多外部文档源真实验证，以及对高风险饮食建议增加人工审核或更强规则兜底。
