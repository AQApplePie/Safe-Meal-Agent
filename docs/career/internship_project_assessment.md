# SafeMeal：Python 后端与 Agent 应用开发实习投递评估

评估日期：2026-10-09。目标岗位：Python 后端 + Agent 应用开发。依据：当前代码、测试报告、部署配置、训练/评测记录，以及企业公开职位说明。此次为只读项目评估与报告整理，没有拆分代码、部署或执行数据库迁移。

## 1. 结论

两部分已具备实习项目投递基础。主要差距在独立交付、真实性能/效果证据和面试可解释性，而不是缺少更多框架。可以开始投递，同时补齐以下高优先级事项；不能据此保证录用。实际是否匹配还受计算机基础、个人贡献、在读资格和可实习时间影响。

当前是一个模块化单体的两个方向，尚非两个已经独立运行的项目。前端、主应用、ApplicationContainer 和 Compose 都同时服务两部分。建议区分为：

- **SafeMeal Recipe Platform**：食谱与用户行为服务。重点证明 SQL、缓存、并发一致性和事件恢复能力。
- **SafeMeal Agent**：饮食约束下的多轮食谱助手。重点证明上下文、工具调用、安全约束、恢复、评测与成本控制能力。

可先保留同一仓库、共享业务契约，增加两个独立入口/运行配置和两份 README。不要求为了简历引入微服务；也不要求重写 Python。若后续拆成两个仓库，应维持清晰的业务契约，避免复制同一模块后分别维护。

两份简历可分别突出对应项目。若同一简历写两项，应说明共享食谱领域基础，不将相同登录、前端和测试成果重复算成两份独立工作。

## 3. Python 后端最需要补齐

### P0：独立轻量运行

目前主应用注册全部路由，ApplicationContainer 会初始化 Agent checkpoint；默认 Compose 依赖 Neo4j/Milvus，并带入模型配置。后端单独展示时负担较重。

验收：仅 API + MySQL + Redis 即可启动、迁移、导入演示数据和跑 smoke test；不要求 LLM/Embedding 密钥，不初始化 Agent checkpoint。提供后端自己的依赖/配置清单和启动文档。

### P0：真实 MySQL 联调与并发证据

真实 Redis 测试已有，MySQL 8 事务锁、唯一键、隔离级别、死锁和迁移不能仅用 SQLite 结果证明。

验收：隔离 MySQL 测试库，真实 migration up/down；同用户并发点赞不重复、多用户计数正确、重复取消正确；行为/outbox 同事务回滚；多实例消费与过期租约恢复。对死锁/锁等待失败明确说明是否重试、如何返回和如何恢复。

### P0：性能实验与 SQL 分析

并发正确性测试不等于 HTTP 吞吐压测。当前未发现能支撑“高并发”“提升 xx%”的完整实验记录。

验收：固定机器、数据规模、并发数、请求比例、预热/持续时间；至少测试列表、详情、交互写入和榜单读取。记录吞吐、p50/p95/p99、错误率、缓存命中、数据库查询次数与资源占用；真实 MySQL `EXPLAIN ANALYZE` 比较典型查询；缓存开/关、冷热缓存和索引优化前后分别报告。

可选择 10 万食谱、100 万行为记录作为自建测试规模；这是建议实验规模，不是现有数据或必须门槛。缓存热点合并当前为同进程锁条带，多进程/实例缓存回源压力须单独验证。不要将其表述为已实现分布式热点互斥。

### P1：运维闭环

已有日志、健康检查、重试和死信接口实现，但缺少持续指标与告警证据。

验收：能查看 API 延迟/错误率、缓存命中、outbox 积压和最老事件年龄、消费失败与死信数量；记录一次 Redis 故障→SQL 保留事件→恢复投递的过程，明确检测、排查和恢复操作。不必引入庞大的监控平台，最小指标和报告即可。

### P1：目录管理业务闭环

现有用户消费侧完整，目录维护主要依赖种子数据与已有仓储能力。管理侧新增/编辑/上下架、角色权限、审计与缓存失效，可形成更完整的平台故事。

这是第二阶段增强，不是投实习的硬性前置。若实现，应把授权、并发更新与缓存一致性一并设计；不需要为了项目规模增加支付、秒杀或商城。

## 4. Agent 应用开发最需要补齐

### P0：有基线的端到端效果评测

已有 20 条回归 manifest、组件测试、失败修复与历史 E2E，说明关注可靠性。它们还不能回答在广泛新任务上的成功率、与简单方案相比的收益。

验收：先整理 100–200 个固定任务，覆盖单菜、多约束、过敏、多轮指代、菜单局部替换、知识问答、工具失败、提示注入与身份隔离。保留题目来源、标准答案/判定器、模型/Prompt/代码版本；区分开发集与冻结测试集。

对关键场景重复运行，例如每题 3 次，并与“同模型单轮 Prompt”“简单检索/工作流”基线比较。报告任务成功率、约束满足率、工具调用正确率、跨轮状态保持、安全违规和恢复成功率；人工抽样校准判定器。不能只由模型给自己打分，也不能将建议样本规模写成现有成果。

### P0：耗时、Token 与成本对照

代码已有 token 和费用预算，不应再笼统说缺少成本控制。缺的是运行结果、分布与改进对照。

验收：每个任务保存 trace、模型/工具调用次数、输入输出 token、定价来源、首响应与总耗时；按简单/复杂任务分组报告 p50/p95 和平均成本。比较策略优化前后，在同一任务集上说明收益与成功率变化；供应商缺少 usage 时明确标记未知。

### P0：人工审批前端闭环

后端已有 `/chat/resume`、human approval 与 pending_calls，但当前 App 只处理普通流式回复，没有审批/拒绝/恢复入口。

验收：展示待执行动作；用户批准或拒绝后恢复同一 checkpoint；刷新页面后仍可识别待审批状态。演示工具故障、模型超时、checkpoint 恢复与越权拒绝。记忆查看/修改和知识上传/摄取状态入口也可使已有后端能力更容易展示。

### P1：检索质量与消融

已有混合检索/RRF 等实现，组件数量不能证明其效果。

验收：标注查询与相关文档，报告 Recall@K/MRR 等召回指标和最终答案依据；对 BM25、向量、混合、重排做小规模消融。检查文档切分、引用对应、权限过滤和恶意文档指令的处理。保留失败样本和改进依据。

### P1：NLU 微调的泛化验收

训练 README 记录 4,800/600/600 数据划分、实体隔离、LoRA 参数和低 loss，独立行为验收为 6/6；这些是起点，不是完整泛化证明。

验收：基础模型、微调模型、规则回退在同一冻结测试集上比较意图准确率、字段/约束 F1、指代正确率、JSON 合法率、延迟。增加人工编写的未见表达和真实任务；检查模板/分组泄漏，而不只检查实体 ID 不相交。明确模型不可用时规则回退的占比与结果，不把回退成功归给模型。

LoRA 是应用岗加分项，可以后补，不必把时间转向大规模训练或 Agent RL。

## 5. 共同交付缺口

- **README**：根 README.md 当前缺失，而 pyproject.toml 引用了它。补两个目标清晰的入口说明、架构图、运行命令、演示、技术决策和限制。
- **CI**：有 Makefile，但未发现 `.github/workflows`。建立 lint/typecheck/test/build 的自动验证，集成测试使用临时服务，外部模型评测使用独立受控任务。
- **文档一致性**：target_architecture 仍写 Interaction 未实现；production 的身份键描述还是旧拼接，与最新特殊身份编码不一致。发布前清理或注明历史版本。
- **部署证据**：Compose/K8s 文件不等于上线或多副本 HA。至少完成一次干净环境部署和真实前后端联调，保存过程与验收；没有真实用户就不写生产流量。
- **个人贡献**：准备设计取舍、排错记录、提交/PR 与演示。AI 辅助开发可以如实说明，面试必须能够解释并修改核心代码。

## 6. 优先顺序

1. 两个独立运行入口/配置、README、文档一致性。
2. 后端真实 MySQL 联调、SQL 分析和可重复压测。
3. Agent 固定任务集、基线、成功率/延迟/成本报告。
4. 补审批恢复等关键展示流程，完成一次真实前后端联调。
5. 最小可观测性、CI、故障复盘和演示视频。
6. 再考虑管理侧闭环、检索消融、NLU 模型深化。

## 7. 面试准备与简历边界

后端应能解释：唯一键与行锁各解决什么、MySQL 隔离级别如何影响计数、热点锁为何仅同进程有效、为什么使用 outbox、发布/消费后崩溃如何恢复、为什么至少一次投递仍可有幂等效果、查询索引为什么按该顺序设计。

Agent 应能解释：Workflow 与 Agent 的边界、为什么结构化菜单状态不能仅靠聊天文本、LLM 为什么不能决定最终安全性、工具失败为何不等于查无结果、checkpoint 的恢复语义、规则回退与模型作用、复杂循环相对简单方案有什么实测收益。

这两个方向都仍需 Python/异步/线程与阻塞 I/O、HTTP、Linux、SQL、数据结构与算法基础。项目代码无法单独证明这些面试能力。

可以写：已实现的机制、本人可解释的贡献、149 项后端测试、真实隔离 Redis 故障实验、已有多轮状态修复案例。

需要补证据后再写：万级 QPS、性能提升百分比、线上高可用、真实用户规模、Agent 任务成功率、RAG 效果提升、模型推理成本下降百分比。个人项目归项目经历；真实公司实习归实习经历。
