## 二、面试官追问与投递者回答

### 1. 两个项目是不是把同一项目拆成两条，重复计算工作量？

**面试官：** 两者在哪些方面独立？是否拥有两个仓库、两个数据库和两套部署？

**投递者：** 两者目前位于同一仓库，是共享领域模块的两种应用入口。平台已经有独立 ASGI 入口、16 项直接运行依赖、配置和 Docker Compose，只需 API、MySQL、Redis，不加载 Agent SDK；Agent 入口复用食谱、身份和会话能力，再装配模型、工具和图。拆成两条是为了呈现不同工程问题，不代表两个独立代码仓库或两次重复开发。隔离 Compose 使用独立数据卷与端口，实际部署仍由启动配置决定。

**核验：** 成立。避免口头声称“独立开发两套完全无关系统”。

**证据：** [独立运行报告](../optimization/01_backend_independent_runtime.md)、[平台入口](../../safemeal/platform_main.py)。

### 2. 为什么需要 Agent？直接写 SQL 加一个 Prompt 不行吗？

**面试官：** 你的对照能证明 Agent 更准确或成本更低吗？

**投递者：** 简单查询用确定性工具更合适，我没有让所有请求都进入模型规划。Agent 主要处理跨轮状态、组合条件、受保护操作审批和执行过程控制。当前小样本里，带完整微型目录的单 Prompt 也达到 36/36 结构通过，不能证明 Agent 更准确。项目证明的是这些控制机制可以实现并验证，是否值得额外复杂度还需要更大独立任务集和成本对照。

**核验：** 这是关键追问。回答“Agent 准确率明显更高”与现有结果冲突。

**证据：** [真实模型对照](../optimization/05_agent_evaluation_baselines.md)、[原始合并报告](../../evaluation_results/agent_live_verified_report.json)。

### 3. 请画出一轮请求的执行顺序，哪些是固定流程，哪些由模型决定？

**面试官：** 为什么要两层图？模型能跳过安全复核吗？

**投递者：** HTTP 先绑定身份，ChatTurnService 保存用户消息后进入外层 Workflow，顺序是请求理解、上下文准备、约束解析、Agent 执行、最终安全复核和记忆保存。内层图负责初始化、规划、必要审批、工具执行、观察、反思与回答。固定安全流程不由模型决定；明确数量推荐等任务可走确定性策略，其他场景再使用模型规划。图有迭代和调用预算，不能无限重试。

**核验：** 源码支持。需要自己能画图，并区分默认构造参数与实际环境配置。

**证据：** [外层 Workflow](../../safemeal/agent/workflow/graph.py)、[内层图](../../safemeal/agent/runtime/orchestration/graph.py)、[确定性策略](../../safemeal/agent/runtime/orchestration/nodes/planner/strategy.py)。

### 4. 用户说“我对花生过敏”和“朋友对花生过敏”，你如何避免记错人？

**面试官：** “今晚别放花生”会永久改变用户偏好吗？

**投递者：** 当前轮条件和长期记忆分开处理。记忆保存要求明确的个人表达，并排除今天、本次、朋友、假设等临时或第三方表达；结构化 RequestFrame 也记录参与者和记忆更新。加载记忆按可信用户身份和所需类型查询，不把所有历史无差别送入模型。这里仍包含规则和关键词启发式，复杂表达不能保证全部识别正确，撤销与歧义需要专门处理和回归。

**核验：** 机制成立，不应声称“所有过敏表达都能准确识别”。

**证据：** [记忆保存节点](../../safemeal/agent/workflow/nodes/save_memory.py)、[上下文加载](../../safemeal/agent/workflow/context/builder.py)。

### 5. “换其中一道素菜，其他保持”怎么保证保留原有菜品？

**面试官：** 如果下一轮新增过敏条件，原有菜单还保留吗？

**投递者：** 我持久化结构化 active_menu，包含配额、已选菜品和候选证据。局部替换只移除目标菜品，合并新结果后重新计算分类配额。最终复核不能仅看新菜，也会按本轮条件检查保留菜品的完整食材证据；新过敏条件使原菜不符合时，不直接发布原完整菜单，而是标明缺额或不完整。

**核验：** 有针对性回归。需解释“保持”仍受当前安全约束限制。

**证据：** [菜单合并](../../safemeal/agent/context/active_menu.py)、[最终复核](../../safemeal/agent/workflow/nodes/safety.py)、[多轮回归](../../tests/evaluation/test_menu_context_modification.py)。

### 6. 名称是“食品过敏安全 Agent”，你凭什么保证用户吃了安全？

**面试官：** 只查主要食材能判断吗？测试通过是否意味着医学安全？

**投递者：** 项目提供的是基于已知配料和声明条件的约束检查，不是医学安全保证。我区分可通过、排除和证据未知；主要食材摘要不能证明完整配料安全，证据不足时不能作肯定安全推荐。数据遗漏、交叉污染和复杂过敏知识不在现有规则的完整覆盖范围内。标题可以描述应用场景，但答辩中不能将回归通过率等同于现实食用安全。

**核验：** 必须保留这条边界。标题建议考虑“饮食约束与食谱助手”，减少绝对安全含义。

**证据：** [安全服务](../../safemeal/agent/safety/dietary_safety_service.py)、[安全记忆测试](../../tests/evaluation/test_safety_memory_scope.py)。

### 7. 重复点击审批按钮，为什么只能有一个请求执行？

**面试官：** 前端 disabled 能解决多实例并发吗？

**投递者：** 前端禁用只是交互保护。服务端先校验用户拥有会话和消息，再以 message_id、approval_id、待审批 metadata 以及未认领状态为条件执行 UPDATE；受影响行数为 1 才取得执行权，同时提交审批决定和审计数据。并发请求使用同一持久化数据库条件竞争，失败请求不继续恢复图。测试中四个并发认领仅一个成功。

**核验：** 有条件更新实现。本次审批专项使用 SQLite，不能说审批 CAS 本身已经做过真实 MySQL 多实例压测；平台的真实 MySQL 租约测试是另一机制。

**证据：** [认领 SQL](../../safemeal/infrastructure/persistence/chat_repository.py)、[审批专项](../../tests/refactor/test_approval_flow.py)。

### 8. 认领审批后宕机，或者工具执行成功但结果没落库，会发生什么？

**面试官：** 是否保证 exactly-once？刷新恢复等于故障自动恢复吗？

**投递者：** 不保证外部副作用 exactly-once。聊天 SQL 与图 checkpoint 是两个持久化边界，认领后中断可能保留 processing；执行错误则可能记为 failed。结果无法确定时禁止自动重放，维护者需要核对审计、checkpoint 和实际副作用。待审批任务在组件重建后能恢复，浏览器刷新能重读状态，但不等于任何宕机阶段都能自动无损继续。后续涉及真实外部写操作，应在下游引入幂等键和结果核对机制。

**核验：** 此限制明确写在报告中。“审批防重”和“所有工具恰好执行一次”必须区分。

**证据：** [恢复用例](../../safemeal/agent/gateway/chat_turn_service.py)、[恢复边界](../optimization/07_agent_approval_resume.md)。

### 9. 120 条案例具体测什么？是不是自己出题、自己判满分？

**面试官：** 能否叫 99.17% Agent 成功率？

**投递者：** 120 条是合成的请求理解契约案例，验证数量、类别、约束和指代等字段，不是完整 Agent 的最终答案准确率。比较弱关键词、无上下文规则和带上下文生产规则，后者为 119/120；失败案例保留。dev/test 按案例拆分，有模板主题重叠，而且测试集已经被查看，所以不能包装成未知留出集或独立泛化结论。预期标签不传给被测系统。

**核验：** 数据和脚本可检查。禁止将该数字简化为“Agent 准确率 99.17%”。

**证据：** [数据集](../../tests/evaluation/datasets/request_contract_v1.json)、[离线评测脚本](../../scripts/evaluate_agent_contracts.py)。

### 10. 12 个真实任务得到什么结果？失败评分器是否被你改到通过？

**面试官：** 36/36 为什么不写简历？最初的知识错误后来怎么处理？

**投递者：** 12 个任务各重复三次，重复不能算独立任务。最终结构评分单 Prompt 36/36、一次检索 33/36、Agent 36/36；评分器修正应用于前后两组，并保留初始输出。结构评分曾漏掉知识事实错误，定点核对后发现组胺表述问题；后续修正回答约束，三次完整 Agent 与六次给定 FDA 证据的网关回答通过该核心事实核对，但这不是整个评测集重新完成独立专家事实评审，所以不写整体满分。

**核验：** 能诚实说明失败比背诵满分有说服力。最后报告由两个夹具修正批次组成，也应承认。

**证据：** [真实评测边界](../optimization/05_agent_evaluation_baselines.md)、[定点事实核对](../../evaluation_results/agent_retrieval_manual_review.json)。

### 11. BM25、向量和 RRF 分数有什么区别？为什么修复不能简单改成 0.01？

**面试官：** 混合之后为什么丢了证据？公式是什么？

**投递者：** 原代码融合后仍用原 score 与 0.7 比较，BM25 分数与向量相似度并不在同一尺度，RRF 又是排名融合分数。RRF 对各通道排名累加 1/(k+rank)，不是把原始分数相加。我把相似度阈值只应用于向量通道，再做融合，并让同通道重复片段只投票一次；改成另一个统一阈值仍没有跨尺度依据。重排只能排序已经召回的原始片段，不能补造正文。

**核验：** 实现和缺陷复现成立。生产向量默认 metric 为 IP，答辩时不要未经检查就称它必然是余弦分数。

**证据：** [知识检索用例](../../safemeal/modules/knowledge/application/knowledge/document_knowledge_service.py)、[RRF](../../safemeal/modules/knowledge/application/knowledge/hybrid.py)。

### 12. 消融到底用了什么模型？为什么不能证明生产 RAG 效果？

**面试官：** 有没有真的调用 Embedding 和 Reranker？混合是否优于单路？

**投递者：** 实际尝试了配置的嵌入接口，但 text-embedding-v4 被错误继承到 DeepSeek 地址，返回 404，没有成功的生产向量或重排效果。成功消融使用本地字符 TF-IDF、精确余弦存储、真实 SQLite BM25 和 token 覆盖参考重排，10 篇短文、20 个标注问题，dev/test 共享主题。它验证修复机制，不证明生产语义模型表现。取消参考向量阈值后，test 向量 MRR@3 为 1.0，混合为 0.95，参考重排为 0.933，没有证明混合或重排更好。

**核验：** 本项目最弱的效果证据。简历目前使用“本地参考消融”是准确的，不能删除限定词。

**证据：** [消融报告](../optimization/08_agent_retrieval_quality_ablation.md)、[接口状态](../../evaluation_results/agent_retrieval_provider_status.json)。

### 13. “前置权限过滤”怎么做？有引用就代表答案可信了吗？

**面试官：** 模型能伪造 tenant_id 吗？分页后过滤有什么问题？

**投递者：** HTTP 根据认证 Principal 绑定请求范围租户，ContextVar 传入工具调用；工具 schema 不接受模型 tenant_id。BM25 在参数化 SQL 中过滤 public 和当前租户后再 LIMIT，避免其他租户高排名占满候选；向量查询带租户过滤，用例层再检查返回归属。来源保留 document_id/chunk_id，但它仅表示返回的证据集合，不能证明回答每句话都受该片段支持。注入提示的边界测试也不等于真实模型对全部攻击安全。

**核验：** 访问控制与引用定位成立，逐句支持验证尚未实现。显式 vector filter_expr 时关闭词法合并，不能声称两路都支持同一表达式。

**证据：** [可信 scope](../../safemeal/agent/runtime/tools/knowledge_scope.py)、[BM25](../../safemeal/infrastructure/retrieval/sqlite_bm25.py)、[来源归因](../../safemeal/agent/runtime/aggregation/sources.py)。

### 14. 技术栈写 SSE，是否真的边生成边展示？Token 和成本怎么算？

**面试官：** 第一 Token 多快？调用次数是否等于账单请求数？

**投递者：** 当前 Workflow 抑制模型回答片段，最终安全复核后才通过 SSE 分块发送回答，同时可以发送工作流进度；不宣传未经复核的逐 Token 输出或首 Token 延迟。观测记录工作流与模型阶段耗时、输入/输出/缓存 Token 和完整性。价格缺失时 estimated_cost 为 null，不当成零；SDK 内部重试也不能仅靠网关计数精确还原账单次数。当前知识问答有 Token 记录，但对应模型价格未配置，不能声称实际节省金额。

**核验：** SSE 契约成立，但“实时模型 Token 流”和“成本已优化”没有依据。

**证据：** [Workflow](../../safemeal/agent/workflow/runner.py)、[HTTP SSE](../../safemeal/interfaces/http/answer_stream.py)、[用量报告](../optimization/06_agent_latency_token_cost.md)。

### 15. 8 个并发请求从 8 次回源变成 1 次，是怎么测到的？

**面试官：** 是因为预热命中了缓存吗？跨进程是否同样只有 1 次？

**投递者：** 冷缓存并发突发与预热后的稳态测量分开记录。相同查询生成相同 cache key，在锁条带内二次检查缓存，第一个请求加载并填充，后续读到结果，因此同一进程内 8 个请求只回源一次。锁是 64 条线程 Lock，不是 Redis 分布式锁；不同 worker 仍可能各自回源。这个数字也不代表 Redis 故障且 L1 关闭时仍能合并所有请求，因为当前合并依赖二次缓存命中。

**核验：** 对照有原始记录。正确理解回源次数与 SQL 次数：详情一次回源对应 3 条 SQL，列表对应 4 条。

**证据：** [缓存装饰器](../../safemeal/infrastructure/cache/recipe_repository.py)、[冷缓存对照](../optimization/03_backend_performance_sql.md)。

### 16. L1 和 Redis 如何一致？缓存 key 为什么不带用户？

**面试官：** 目录更新是否立即可见？随机 ID 攻击是否被完全挡住？

**投递者：** 这里缓存的是共享食谱目录，不是个人收藏或租户私有文档；列表的过滤、排序、分页参数整体参与 key，详情以食谱 ID 标识。L1 有容量上限和短 TTL，命中不续期，Redis 使用较长 TTL 加抖动，未找到详情用更短负缓存。当前主要靠过期实现最终更新，没有完整的多实例主动失效机制；如果加入私有食谱或目录编辑，必须重新设计权限 key 和失效协议。负缓存只降低重复不存在 ID 的回源，随机高基数请求仍需限流等措施。

**核验：** 现有目录范围内成立，不能声称强一致缓存或已解决任意穿透攻击。

**证据：** [缓存实现](../../safemeal/infrastructure/cache/recipe_repository.py)。

### 17. 731.5 ms 降到 127.8 ms，具体减少了什么工作？

**面试官：** 原查询和新查询结果一致吗？这是接口延迟还是 SQL 延迟？

**投递者：** 原榜单先关联食谱再聚合，50 万点赞事实会产生约 50 万次食谱主键查找；改成按租户过滤并先按 recipe_id 聚合，再关联名称，主键查找约减少到 10 万次，事实扫描本身仍存在。先校验新旧结果相同，再在暖连接下交替采样，以十轮中位数比较。数字是本地真实 MySQL 热门榜单 SQL 耗时，不是完整接口 p95；18 个 SQL 等价回归覆盖模式、租户和 limit。

**核验：** 这是平台项目最有力的答辩点。必须自己能写出聚合子查询和解释执行计划。

**证据：** [聚合仓储](../../safemeal/infrastructure/persistence/ranking_repository.py)、[原始性能记录](../../evaluation_results/backend_performance.json)。

### 18. 为什么索引是 difficulty,total_time,id？分页也提升了 7.5 倍吗？

**面试官：** 索引有没有代价？如何隔离索引收益？

**投递者：** 代表查询先按难度等值过滤，再按耗时范围过滤并按耗时、ID 排序，因此建立该复合索引。旧计数约扫描 33376 行再筛选，新计划覆盖范围扫描约 7515 行，计数中位数 9.03→1.20 ms。分页本来就能利用耗时索引提前停止，收益只有 0.546→0.495 ms。对照在临时 MySQL 使用 IGNORE INDEX 保留旧索引集合，没有删除生产索引。新增索引有存储和写维护成本，本轮没测食谱写入吞吐。

**核验：** 数字成立，不能将计数收益推广到所有分页/排序。

**证据：** [SQL 对照说明](../optimization/03_backend_performance_sql.md)、[索引迁移](../../safemeal/infrastructure/persistence/migrations/versions/20261009_0014_recipe_difficulty_time_index.py)。

### 19. 你能承诺平台支持多少 QPS？“百万级行为”是不是百万用户？

**面试官：** 负载时长、并发和数据分布是什么？JWT、消费者是否一起测了？

**投递者：** 100070 条食谱、50 万点赞事实和50 万浏览历史是合成数据，不是真实用户规模。HTTP 实验是同机单 worker、并发 1/8、每场景 1 秒预热加 5 秒闭环测量，各场景单一接口。20 个场景累计 79234 次测量请求、零错误，但使用固定身份注入，未测 JWT/限流，也没同时运行消费者。它支持条件明确的局部性能对照，不能承诺线上容量、长期稳定性或百万用户。

**核验：** 不宜额外给简历添加“高并发百万用户”或固定生产 QPS。

**证据：** [完整实验条件](../optimization/03_backend_performance_sql.md)。

### 20. 为什么数据库提交后直接发消息不够？Outbox 如何处理崩溃窗口？

**面试官：** XADD 成功但 published 没写回，或者 Redis 丢数据怎么办？

**投递者：** 数据库与 Redis 之间没有同一事务。业务事实和 outbox 在同一 SQL connection/transaction 提交，relay 再投递只有 event_id 的通知。XADD 后未标记发布会导致重复，消费者按 SQL 事件状态处理；发布成功但 Redis 数据丢失时，SQL 未完成事件会在到期后再次投递。完成事件持久去重，不依赖 Redis 去重状态。前提是 SQL 本身可用且已提交，数据库未提交的写入不能算成功。

**核验：** 该方案是至少一次通知，不是跨 MySQL/Redis 的分布式原子事务。

**证据：** [Outbox](../../safemeal/infrastructure/persistence/behavior_outbox.py)、[投递与消费](../../safemeal/infrastructure/messaging/behavior_worker.py)。

### 21. 去重、租约和 fencing 分别解决什么？为什么重复消息可以 ACK？

**面试官：** 旧消费者醒来会不会覆盖新消费者结果？

**投递者：** claim 通过 SQL 条件 UPDATE 检查未完成、未死信、重试到期和租约过期，取得新的 token；finish 还要求 token 匹配且租约未过期，旧消费者不能把新租约标记为完成。刷新榜单也有独立 Redis 租约，发布脚本检查 token 并原子替换快照。重复、已完成或租约竞争通知可以 ACK，因为未完成事实仍在 SQL 中，后续可以再次投递。刷新操作读取事实并发布绝对快照，不对重复通知直接加分。

**核验：** SQL 事件与 Redis 快照是两套不同租约，必须分开解释；不能拿 SQL finish token 当作所有外部写操作的全局 fencing。

**证据：** [事件状态](../../safemeal/infrastructure/persistence/behavior_outbox.py)、[快照发布](../../safemeal/infrastructure/cache/ranking_store.py)。

### 22. 每条点赞都重算整个租户榜单，百万数据时消费得动吗？

**面试官：** 异步是不是只是把性能问题移到后台？

**投递者：** 当前通知触发租户 today/popular 两种榜单刷新，主要优先保证可重建和重复处理正确，确实有重复聚合成本。现有百万行 HTTP 压测没有启动消费者，不能拿它证明事件吞吐。扩展时可按租户合并短时间通知、批量刷新或建立增量聚合，并保留全量校准路径，但这些是后续方案，没有实现。是否需要增量化应先测刷新时长、积压年龄和实际写入速率。

**核验：** 当前架构最明显的扩展限制。简历写“一致性与恢复”成立，写“高吞吐事件系统”不足。

**证据：** [消费入口](../../safemeal/infrastructure/messaging/behavior_worker.py)、[租户刷新](../../safemeal/modules/interaction/application/ranking_service.py)。

### 23. Redis 故障时业务还能用吗？为什么 readyz 变成 503？

**面试官：** 如果 Redis 同时承担限流，你的降级还成立吗？

**投递者：** 演练未启用 Redis 限流，验证了缓存故障回源 SQL、事务继续保存行为与 outbox、恢复后原 worker 自动消费。默认启用 Redis 限流时采用 fail-closed，Redis 不可用会在 handler 前返回 503，故障期间被拒绝的写入不会新增事件；故障前已提交事件仍可恢复。livez 表示进程存活，readyz 检查配置依赖，因此 Redis 不可用时 readyz=503，编排系统可能摘流。不能将演练扩展成“所有接口零影响”。

**核验：** 简历的恢复句需要答辩补充条件，或直接写“在关闭 Redis 限流的故障演练中”。

**证据：** [演练与限制](../optimization/04_backend_operations_recovery.md)、[真实阶段记录](../../evaluation_results/backend_operations_fault_drill.json)。

### 24. 为什么还要真实 MySQL 测试？SQLite 没暴露哪些缺陷？

**面试官：** 死锁如何重试？会不会重复外部操作？

**投递者：** 真实 MySQL 揭示了迁移降级提前删除外键依赖索引、DATETIME(0) 舍入使事件暂时不能认领、RR 旧快照导致历史 UPSERT 后读取过时值等问题。我修正降级顺序、使用 DATETIME(6) 并在所需位置使用当前读。锁冲突仅对明确的 1205/1213 做有限整事务重试，重建事务，而不是在已经失败的事务里只重试单条 SQL；重试闭包只含数据库操作，不含 Redis、模型等外部副作用。

**核验：** 真实联调报告支持，适合深入追问数据库原理。

**证据：** [MySQL 联调](../optimization/02_backend_mysql_integration.md)、[事务重试](../../safemeal/infrastructure/persistence/transaction_retry.py)。

### 25. 你写 RabbitMQ、MCP、Multi-Agent、Maven 熟悉，项目里在哪里使用？

**面试官：** 是否能展示配置、协议交互或自己的实现？

**投递者：** 这两个项目实际消息链路是 Redis Streams，编排是单 Agent，不是 Multi-Agent；工具注册表也不能因为功能类似就称为 MCP。Maven 不是这两个 Python 项目的构建工具。如果我在其他项目中用过，需要拿独立证据说明；仅凭本项目不能支撑这些技能的熟练表述。没有其他实操材料时，我会删除或降级这些词，改写为已实现的 FastAPI、SQLAlchemy、Redis Streams、Tool Calling 和 LangGraph。

**核验：** 当前技能栏是整份简历风险最高的部分。缺少项目证据不等于候选人一定不会，但“熟悉”需要自己承担追问。

### 26. FastAPI 是异步的，为什么还用线程池？你真的熟悉多线程并发吗？

**面试官：** Session 能跨线程共享吗？GIL 是否使并发数据库认领安全？

**投递者：** 当前部分 SQLAlchemy/Redis 适配器是同步阻塞调用，async 聊天链路通过 asyncio.to_thread 将对应事务操作移出事件循环，异步工具调用再用 semaphore 控制并发。数据库事务内创建和使用自己的会话/连接，不把同一个可变 Session 作为并发共享对象。进程内 Lock 只解决本进程缓存回源竞争，跨进程正确性依赖数据库约束和条件更新，不能依赖 GIL 代替业务同步。多线程不自动提高 CPU 密集任务性能，也不能消除阻塞连接池的容量限制。

**核验：** 源码能支撑线程池应用；候选人能否解释事件循环、同步阻塞、连接池及会话生命周期，需要独立问答确认。

**证据：** [聊天协调](../../safemeal/agent/gateway/chat_turn_service.py)、[工具执行器](../../safemeal/agent/runtime/tools/runtime.py)。

## 四、面试前准备与证据定位
