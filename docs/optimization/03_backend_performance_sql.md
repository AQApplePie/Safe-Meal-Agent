# 文档 4/9：传统后端第三项——性能实验与 SQL 分析

## 1. 交付结果

新增 `make bench-backend`，生成固定规模合成数据，通过真实 TCP HTTP 测试列表、详情、点赞写入与榜单读取，并记录吞吐、p50/p95/p99、错误、回源/缓存命中、SQL 次数和容器资源快照。真实 MySQL `EXPLAIN ANALYZE` 与同连接交替采样支持三处改进：榜单先聚合再关联、列表计数按需关联菜系、新增难度/耗时复合索引。

最终性能专项 **1 passed**，20 个场景共 **79,234 次测量请求、0 错误**。全量回归 **452 passed、2 skipped**，其中原 20 项真实 MySQL/Redis 验收全部通过。Ruff、7 个本轮 Python 文件格式检查、Mypy（302 个源文件）和 diff 检查通过。

两项跳过分别是明确 opt-in 的性能实验（已单独成功执行）与需真实模型凭据的 DeepSeek E2E；不代表两项验证失败。性能专项另有 2 条来自 uvicorn/websockets 的弃用提示。

| 项目 | 本次条件 |

| 基础设施 | MySQL 8.0.46、Redis 7.4.11；自有临时容器与回环动态端口 |

| HTTP | 真实 uvicorn/FastAPI 路由、业务服务、SQL 仓储；API 与负载生成器在同一 Python 进程；单 worker；客户端 `trust_env=False` 直连，避免本机代理 |
| 身份与后台任务 | 使用测试依赖注入提供固定租户/每客户端独立主体；不测 JWT/OIDC、限流、中间件与消费者；没有启动异步刷新/投递 worker |

| 缓存 | 关闭、Redis（L1 TTL=0）、Redis＋L1；Redis TTL=60 秒＋现有抖动；L1 TTL=1 秒；容量 256；榜单缓存单独由事实刷新预热 |
| SQL | 暖缓冲/连接后 10 次采样，各轮交替先后顺序；读取完整结果校验相同，再比较中位数；保留真实 `EXPLAIN ANALYZE` 文本 |
| 隔离级别 | REPEATABLE-READ；测试引擎连接池 32、无溢出；会话锁等待 1 秒；不修改生产默认 2 秒 |

数据行数以实际 COUNT 校验，而不是使用 information_schema 的估算。1,000,000 行 `benchmark_numbers` 与 10 行 `benchmark_digits` 只用于自有库生成数据，容器删除后一起消失。MySQL 数据目录使用 tmpfs，Redis 不做持久化；Docker 内存统计因此也包含临时数据库页。未设置独立容器 CPU/内存上限。

短时闭环测量、单进程与均匀合成数据有明确边界：不能据此声称生产容量、持续稳定运行、JWT 全链路吞吐、真实用户量、多实例热点互斥或消费者吞吐。不同接口分别测量，尚未测多接口混合流量。本文 req/s 是这个实验条件下的 HTTP 结果。

## 3. 实际代码改进与 SQL 证据

| 对照 | 优化前中位 ms | 优化后中位 ms | 前/后比值 |
|---|---:|---:|---:|
| 热门榜单：先关联再聚合 → 先聚合再关联 | 731.508 | 127.796 | 5.72× |
| 列表计数：移除无菜系筛选时的关联（忽略新增索引以单独比较） | 9.553 | 9.096 | 1.05× |
| 难度＋耗时计数：旧索引集合 → 新复合索引 | 9.029 | 1.203 | 7.50× |
| 难度＋耗时分页：旧索引集合 → 新复合索引 | 0.546 | 0.495 | 1.10× |


### 3.1 榜单先聚合、后关联

`SqlAlchemyRankingRepository.aggregate` 先按租户及日期过滤行为事实，按 `recipe_id` 计数，再关联目录取名称与排序。不再让每一条行为事实都先查食谱目录，也不再在行为聚合键中携带名称。

真实热门榜单计划：扫描 500,000 条行为事实不变；食谱主键查找从 **500,000 次降到 100,000 次**。中位 SQL 耗时由约 731.5 ms 降至 127.8 ms，约减少 82.5%；这一数字只适用于本次热门榜单 SQL 对照，不能推广到所有请求。排序仍按分数降序、食谱 ID 降序，LIMIT=1001；未提前限制事实或改变计分。

今日榜单仍在聚合前应用 UTC `[start,end)`；点赞＋收藏仍分别计分；租户过滤、零结果、同分次序和当前目录名称语义保留。18 个旧/新 SQL 等价回归覆盖 2 种模式、3 类租户、3 种 limit；真实 MySQL 既有排名/恢复用例也通过。

### 3.2 列表 COUNT 移除多余关联

只有菜系筛选需要在 COUNT 中关联 `cuisines`。页查询继续关联菜系并批量读取食材与步骤，返回规范的食谱对象，因此两个入口与 Agent 查询契约保持一致。食材筛选仍为 EXISTS，不会由于多食材产生重复计数。

单独比较时两条 SQL 均忽略新增复合索引，避免混合索引收益：约 9.55 → 9.10 ms，收益较小；主要价值是减少无必要工作。回归验证 `cuisine_id=NULL` 的食谱仍计入未筛选总数、菜系筛选正确、菜系＋食材组合正确、未知菜系返回零。

### 3.3 难度＋耗时复合索引

新增迁移 **`20261009_0014`**，索引 `ix_recipe_browse_difficulty_time_id(difficulty,total_time,id)`，迁移链从 0013 延续。

对照不删除生产索引：在临时 MySQL 中，以 `IGNORE INDEX (ix_recipe_browse_difficulty_time_id)` 保留旧索引集合，再与正常优化器使用新索引比较。代表查询为 `difficulty='easy' AND total_time<=30`，分页按 `total_time,id` 升序、LIMIT=20。

计数计划从旧难度索引扫描约 33,376 行后过滤，变成复合索引覆盖范围扫描 7,515 行，约 9.03 → 1.20 ms（减少约 86.7%）。分页本来可借已有耗时索引提前停止，新索引收益仅约 0.546 → 0.495 ms，接近网络往返开销，不宣称同等比例收益。

新索引增加存储与食谱 INSERT/UPDATE 维护成本；本轮没有测目录写入吞吐。多个难度、倒序、名称包含搜索、其他排序不一定获得同样收益。保留原索引以支持其他筛选路径。SQLite 专项与真实 MySQL `head→base→head` 验证升级/降级、索引字段和原目录保留；用户现有数据库尚未升级，迁移 head 现为 0014。

榜单在 Redis＋L1 组仍是同一 Redis ZSet 方案，L1 只影响食谱列表/详情；两组榜单结果的差异是不同试次的波动，不能归因于 L1。点赞写入与食谱缓存无关，只测一组，包含真实事务与 outbox INSERT；每个测量请求 4 条 SQL，用户间争用同一个食谱锁。后台消费者没有运行，通知积压没有计入此处吞吐。

未缓存列表每个成功请求 4 条 SQL，详情 3 条 SQL；代码逐场景断言查询预算，没有随页内食谱条数变成 N+1。暖缓存列表/详情各组的仓储回源为 0、SQL 为 0，定义为 `1 - 回源次数 / 成功读取请求数` 的缓存命中率均为 100%。这是重复访问两个热点键的实验，不是实际用户全量命中率，也没有分别把 Redis 与 L1 命中率合并伪装成两个独立指标。

真正冷缓存的首次并发突发单独测量，未与 5 秒稳态统计混为一谈：

| 场景 | 缓存 | 同时请求 | 数据库回源 | SQL 次数 |
|---|---|---:|---:|---:|
| 列表 | 关闭缓存 | 8 | 8 | 32 |
| 详情 | 关闭缓存 | 8 | 8 | 24 |
| 列表 | Redis（L1 TTL=0） | 8 | 1 | 4 |
| 详情 | Redis（L1 TTL=0） | 8 | 1 | 3 |
| 列表 | Redis＋L1 | 8 | 1 | 4 |
| 详情 | Redis＋L1 | 8 | 1 | 3 |


每组冷缓存只有 8 个样本，保留原始耗时但不据此报告稳定 p99。热点合并只在单进程 64 条锁条带内生效；未实现或验证分布式回源互斥。缓存机制本身沿用原实现，本轮补充测量证据。

## 5. SQL 局限与资源

深 offset 的实际计划仍扫描 90,020 行后丢弃前 90,000 行。此处保留现有公共 offset 契约，不引入另一套分页协议；长历史已经使用独立 keyset 查询。名称包含/食材包含查询不能保证普通 BTree 有高选择性，后续需要结合实际检索需求，而不是盲目增加索引。

每个 5 秒窗口在约第 2 秒请求 `docker stats --no-stream`，记录 MySQL/Redis 的 CPU、内存、网络和块 I/O；这是期间单次快照，不能当作持续峰值。CPU 百分比按 Docker 定义记录，100% 约一个 CPU 核；网络/块 I/O 是累计值，未把它们误报为瞬时速率。原始记录也包含 Redis used_memory、进程结束 RSS（API 与负载生成器共享约 167.8 MiB）和每张表的估计占用；RSS 为结束时值，不是峰值，不能单独当作生产 API 内存。

## 6. 架构审阅

| 边界 | 审阅结果 |
|---|---|
| 数据访问 | 两项查询改动位于 infrastructure persistence；索引只由增量 Alembic 迁移管理；没有把 SQL 放进路由或业务服务 |
| 公共契约 | RecipeQuery、RecipeSearchResult、RankedRecipe、HTTP DTO 与排序/分页规则不变；食材与步骤仍通过两个批量查询读取 |
| 缓存与事实 | 装饰器只缓存读取；点赞与 outbox 同事务边界不变；排名仍由 SQL 事实计算后发布，不根据测试事件次数加分 |
| Agent 与独立后端 | 未新增模型依赖、SDK 初始化、Agent 分支或平台配置耦合；共享仓储优化同时适用于两入口；全量回归包含 Agent 与独立运行边界测试 |
| 实验隔离 | 负载计数、SQL event listener、固定 actor、资源采样只在 opt-in 测试中；不引入业务层测试开关；没有把压测观察计数器当成已完成生产监控 |
| 测试设施 | 复用上一项自有服务 fixture，只增加按调用模块选择报告文件的能力，以免性能实验覆盖 MySQL 联调记录；不接受外部 DATABASE_URL，也不清空用户 Redis |

审阅结论：改动符合当前“interfaces → modules application/ports → infrastructure，bootstrap 装配”的架构。没有以简化列表为由删除 Agent 需要的规范食谱字段。
