# Agent 第一项：固定评测集与离线基线（第 6/9 份文档）

初版日期：2026-10-09；真实模型补齐：2026-10-10。本项已交付 120 条离线契约案例和 12 条真实模型诊断任务的三组对照。修复了三处业务链路缺陷；知识回答仍存在一类准确性风险，不能宣称完整 Agent 效果已全面验证。

## 问题与实现

原有 20 条回归清单保留。新增 120 条人工定义标准答案的合成任务，覆盖数量/类别、详情字段、菜单人数/配额、多轮指代、过敏、临时偏好、知识意图与域外请求。案例没有来自真实用户流量，不能代表真实任务分布。模板生成的变体存在相关性，120 条不等于 120 个独立语义场景。

数据文件位于 [request_contract_v1.json](../../tests/evaluation/datasets/request_contract_v1.json)，包含稳定 ID、来源、输入、历史、标准答案、分组与 split。按组交替划分为开发集 61 条、测试集 59 条；SHA-256 文件校验输入和答案整体，改动须发布新版本。测试集已经在本轮运行并查看，后续调参不得再把它宣传成未知的独立留出集，应另建 v2 留出集。拆分按案例进行，同模板族可能跨集合，不能声称对未知表达的泛化。

[evaluate_agent_contracts.py](../../scripts/evaluate_agent_contracts.py) 直接调用生产 RequestUnderstandingService，不复制业务实现。评分使用明确字段相等、必须存在的过敏约束与禁止持久化的记忆值，预期答案不进入被测系统。每条运行三次，输出逐条预测、失败字段、分组分母、代码 revision、dirty 状态、所有 safemeal Python 源码 SHA-256、数据版本和 Python 版本。无模型、无 Prompt、无数据库、无外部网络调用。

三组对照：

- stateless_keyword：只识别“推荐”和阿拉伯数字数量的弱基线，仅用来检查评分可区分差异，不是有竞争力的模型基线。
- stateless_rules：与生产理解器相同的规则代码，但不提供历史；控制变量是上下文。
- production_rules：生产规则理解器，提供各任务自己的历史。历史为人工固定输入，并非先前 Agent 回答自动产生，因此不测对话错误累积。

## 实测结果

| 系统 | 全集每次通过/总数 | 全集通过率 | 测试集每次通过/总数 |
|---|---:|---:|---:|
| 弱关键词基线 | 5/120 | 4.17% | 2/59 |
| 无上下文规则 | 109/120 | 90.83% | 54/59 |
| 带上下文生产规则 | 119/120 | 99.17% | 59/59 |

三次重复完全一致，代表确定性复现，不代表随机模型稳定性；统计分母应按唯一案例计算，不能把三次重复算作三倍样本。无上下文规则在 10 条指代案例上全部失败，带上下文全部通过。全量 1 条失败为 A113“如何保存食材”，生产规则判为 recipe_detail，标准答案为 knowledge。保留预测和失败，没有修改生产规则或标准答案来追求满分。测试集满分也不意味着所有用户输入都被正确理解。

证据：[全集对照](../../evaluation_results/agent_contract_baselines.json)、[测试集对照](../../evaluation_results/agent_contract_frozen_test.json)、[专项测试](../../evaluation_results/agent_evaluation_pytest.xml)、[全量回归](../../evaluation_results/agent_evaluation_final_regression.xml)。

## 测试与架构审阅

新增 4 个测试检查数据完整性/分组、评分器约束与记忆判定、预测不读取答案、移除上下文确实改变指代、数据篡改校验失败。评测目录共 78 个测试通过。Ruff 检查通过；mypy 检查 305 个生产源码文件通过。全量回归结果见下方最终验收记录。

评测资产在 tests/evaluation/datasets，执行器在 scripts；生产 HTTP、业务模块、Agent 图、模型网关没有增加评测依赖。保持 Agent 依赖业务契约的方向，传统后端独立启动路径不变。未清理有效回归测试，未改动实际环境密钥和用户数据库。已有工具超时、有限重试、过敏作用域等测试继续执行，但它们属于组件契约测试，不纳入上面的任务通过率。

命令（使用项目已安装依赖的 Python 环境）：

```sh
make eval-agent
PYTHONPATH=. python scripts/evaluate_agent_contracts.py --split dev --repeats 3 --output /tmp/agent-dev.json
PYTHONPATH=. python scripts/evaluate_agent_contracts.py --split all --repeats 3 --output /tmp/agent-all.json
python -m pytest tests/evaluation -q
```

CLI 完成评测时返回 0，即使存在语义失败；执行异常返回非零。语义失败保存在结果字段，不能将进程退出码等同于模型验收成功。

## 离线阶段的证据缺口

离线初版没有调用真实模型，没有完成“同模型单轮 Prompt vs 简单检索工作流 vs 完整 Agent”的对照。没有在统一任务集里测最终答案正确率、工具选择准确率、约束满足率、提示注入与跨用户隔离违规率、菜单局部替换、工具失败后的端到端恢复率；已有组件测试不能替代这些指标。请求理解中的 knowledge 标签正确不代表知识回答有依据，过敏字段正确不代表最终菜谱安全。

后续应新增真实端到端任务与独立留出集、固定模型/温度/Prompt/检索快照，接入同一套输出判定，记录逐轮工具轨迹，并由人工抽样校准判定器。当前可写入简历的表述是“建立 120 条离线请求理解契约评测与上下文消融，定位知识意图识别缺陷”，不可写“Agent 成功率 99.17%”或“相比同模型提升效果”。

## 离线初版验收记录

全量回归 **445 passed、25 skipped、0 failures、0 errors**（12.43 秒）。25 个跳过项属于显式启用的外部模型、真实 MySQL/Redis 或性能测试；本轮没有重新执行上一阶段的 Docker 故障演练，不能将跳过项算作通过。初次受沙箱限制的运行发生 Redis socket 启动错误，随后在获准的隔离测试环境重跑获得上述结果。专项 **78 passed**。代码差异空白检查通过。

## 2026-10-10：真实模型端到端对照补齐

### 执行范围

新增 [live_tasks_v1.json](../../tests/evaluation/datasets/live_tasks_v1.json)：12 条人工合成诊断任务，覆盖推荐、详情、真实多轮指代、跨轮过敏记忆、菜单配额、局部替换、知识问答、提示注入、工具故障恢复、多约束与缺失食谱。输入与标准答案用 SHA-256 一起冻结，没有向模型提供标准答案。它是开发诊断集，已经用于发现并修复缺陷，不是独立留出集；不能将其满分作为泛化证据。

使用项目已配置的 **deepseek-chat**，三组各重复三次，共 108 个任务执行。每个任务可能包含两轮对话。三组模型温度均为 0；生产 Agent 的回答温度仅在评测实例中覆盖为 0，部署默认未改变。模型名是服务商别名，未锁定其底层模型快照，未来服务商升级可能改变结果。

| 组别 | 实际执行方式 |
|---|---|
| single_prompt | 同模型、固定 Prompt，每轮一次生成；直接提供完整九道合成食谱作为上下文。不是无来源的裸模型。 |
| retrieval_once | 同模型、同 Prompt；用规则解析目标，最多一次精确 SQL 检索，再一次生成；非详情请求直接提供微型目录，不进行多轮工具规划。 |
| production_agent | 真实应用组合根、注册登录、JWT 鉴权、聊天 API、Workflow、LangGraph、生产工具、SQL、长期记忆与最终安全复核。 |

HTTP 使用 ASGI TestClient，不是远程部署的 TCP 负载测试。数据库、检查点、上传目录和账号均在本次临时目录新建；没有使用日常数据库。注册/登录没有被 mock，跨用户使用第二个真实测试账号。Redis、Neo4j、Milvus、外部食谱搜索关闭，因此这不是完整 RAG 评测，也不代表生产 MySQL 的性能。

工具故障只在 recipe repository.search 端口注入 DatabaseUnavailableError，未停止真实数据库；聊天和身份存储正常。Agent 第一轮返回带 database_unavailable 的 HTTP 503，下一轮恢复查询成功。基线收到 source_status=database_unavailable，没有真实数据库故障。这项验证边界退化与后续恢复，不是同一次调用内部自动重试的成功率。

### 结果与真实性

| 组别 | 初始运行，统一修正评分器后 | 修复后自动结构判定 | 纳入最终报告的真实模型请求 |
|---|---:|---:|---:|
| 固定上下文单轮 Prompt | 36/36 | 36/36 | 48 |
| 一次检索工作流 | 33/36 | 33/36 | 48 |
| 生产 Agent | 27/36 | 36/36 | 24 |

分母 36 = 12 条任务 × 3 次重复，不是 36 个独立语义任务。三组共有 120 次真实模型请求；这个数字仅指最终报告纳入的运行，前期连通性、冒烟与初始诊断还产生了额外调用。推荐、详情等 Agent 请求可能走确定性路径而不调用模型，不能把 36 个 Agent 任务当成 36 个纯模型任务。

一次检索工作流三次均在 L04 指代跟进失败；其目标识别没能从自身生成的材料回答里恢复菜名，导致检索为空。单轮 Prompt 可读取完整微型目录，在这个小样本上也全部通过。因此结果没有证明 Agent 比强单轮 Prompt 更准确，更没有证明整体 ROI。

36 次 Agent 跨账号会话写入尝试均返回 404；过敏记忆案例三次均验证了数据库持久化和下一轮约束沿用。此结果只覆盖这组身份场景，不是完整授权漏洞扫描。注入案例没有触发越权工具，Agent 给出能力范围内的引导；不是所有提示注入攻击的防御率。

自动结构判定不等于事实准确。L08 的三次 Agent 回答都出现了关于“加热降低组胺风险、不能完全消除”的误导性表述；FDA 指出，已形成的组胺不能靠加热去除。[FDA 官方资料](https://www.fda.gov/food/hfp-constituent-updates/fda-issues-final-compliance-policy-guide-scombrotoxin-histamine-forming-fish-and-fishery-products)

因此，加入这项定点事实审阅后，Agent 为 **33/36**。这也不是全面的人类准确率：审阅由本轮 Codex 执行，没有食品安全专家面板或独立多人标注。其余案例主要校验合成食谱与结构化约束；知识关键词评分只能证明提到了主题，不能证明每句话正确。该知识风险保留为整改项，需要在知识证据约束/RAG 评测中处理，当前不能宣称食品安全知识回答已验收。

### 修复与架构审阅

1. 详情回答后的指代失败：近期引用解析新增对生产详情标题的识别，避免真实 HTTP 历史没有「引号」时丢失对象。
2. 局部菜单替换丢失其他菜：上下文准备区分“其中一道、其他保持”的局部替换；合并保留同分类剩余槽位与原总配额；最终 Workflow 渲染完整合并菜单。
3. “推荐两道不含花生的鱼”误将鱼当成忌口：饮食约束只读取否定修饰语中的花生，推荐理解保留肯定的鱼类要求。显式“鱼过敏”仍保留，新增反例回归。

保留菜单的安全证据来自服务端持久化候选的完整食材，不仅靠主要食材摘要；按当前轮冻结的饮食要求重新审查。新增测试确认新过敏会阻止发布保留的花生菜，并将配额判为不完整，防止“保持菜单”绕过新约束。

职责仍分布于既有层：引用解析在 Agent context，否定范围在 dietary application，菜品品类在 request understanding，局部替换在 Workflow context/active menu，最终发布在 Workflow safety。HTTP Router 没有新增业务判断，传统后端启动路径没有引入评测依赖。

### 评分器修正与可审计证据

保留初始原始输出；评分修正应用到前后两组，没有修改案例标准答案。修正包括：素汤可以填素菜槽位但一菜只能计一次；预期的数据库 503 不算非预期执行异常；能力范围引导也可构成安全拒绝；按完整标题区分“凉拌黄瓜”和“花生凉拌黄瓜”；材料条目不算未知推荐菜。
