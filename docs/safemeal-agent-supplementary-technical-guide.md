# SafeMealAgent 补充技术点指南

> 基线说明：本文只以项目中的《Agent 学习笔记（按题目类型整理）》和当前 SafeMealAgent 代码为依据，不再参考原始 `Agent.md`。

## 1. 结论：整理版文档有没有实际参考价值？

有，但需要正确定位。

整理版文档适合作为以下三类工作的检查表：

- **架构设计检查**：覆盖 Agent 分层、Planner—Executor—Reflector、工具治理、记忆、Checkpoint 和多智能体边界。
- **工程风险检查**：覆盖结构化输出、工具参数校验、熔断、预算、长任务恢复和高并发保护。
- **上线质量检查**：覆盖评测指标、回归集、过程评测、探针测试和灰度迭代。

它暂时不能直接替代以下内容：

- SafeMealAgent 的业务需求与食品安全风险模型；
- 具体接口、数据模型、时序图和部署拓扑；
- 可运行的评测集、容量基线、SLO 与告警规则；
- 每个技术点的负责人、完成标准和上线证据。

因此，它的价值不是“照着概念逐条实现”，而是帮助项目识别缺口。真正落地时，每个知识点都必须转换成：**代码边界、配置项、测试样本、可观测指标和验收门槛**。

## 2. SafeMealAgent 当前已经具备什么？

当前项目已经覆盖了整理版文档中的大量核心能力，不需要重复建设。

| 能力 | 当前实现依据 | 判断 |
| --- | --- | --- |
| Agent 闭环 | LangGraph 中已有 initialize、planner、approval、executor、observer、reflector、responder | 已具备 |
| Workflow 与 Agent 分层 | Workflow 负责聊天流程，Agent 负责动态工具决策，通过 Port 和 Contract 通信 | 已具备 |
| 工具治理 | Tool Registry、Tool Policy、参数校验、超时、并发限制、未知工具检查 | 已具备 |
| 长任务恢复 | SQLite/PostgreSQL Checkpoint、审批中断与恢复 | 已具备基础能力 |
| 运行预算 | 最大迭代、工具调用数、模型 Token、成本和总超时 | 已具备 |
| 人工审批 | 生成食谱调用可中断并等待批准或拒绝 | 已具备 |
| 记忆系统 | 会话历史、长期用户记忆、饮食约束和偏好合并 | 已具备基础能力 |
| RAG | Milvus + SQLite FTS5/BM25 + RRF + 可选 Rerank | 已具备 |
| 文档入库 | 上传、异步队列、PDF/OCR、分块、向量及 BM25 替换 | 已具备 |
| 食品安全出口复核 | 基于结构化食材证据做确定性复核，并采用 fail-closed 策略 | 已具备且设计合理 |
| 身份与隔离 | 本地账号、JWT、刷新令牌轮换、OIDC、Tenant 命名空间 | 已具备基础能力 |
| 部署骨架 | Docker Compose、Kubernetes、健康探针、HPA、PDB、NetworkPolicy | 已具备骨架 |
| 自动化测试 | 当前约 85 个测试函数，覆盖 Agent、Workflow、安全、身份、流式和 Checkpoint | 已有较好的单元/回归基础 |

SafeMealAgent 当前真正的问题不是缺少一个新的 Agent 框架，而是缺少把已有能力证明为“可评测、可追踪、可上线、可持续维护”的工程闭环。

## 3. 缺口优先级总览

| 优先级 | 技术点 | 为什么重要 |
| --- | --- | --- |
| P0 | 恢复离线评测与黄金数据集 | 没有它就无法证明修改后更安全、更准确，也无法建立 CI 发布门禁 |
| P0 | 食品安全领域证据与风险模型 | 普通“食材字符串匹配”不足以覆盖衍生物、交叉污染、剂量和来源可信度 |
| P0 | 可复现环境与 CI 质量门禁 | 当前默认环境无法收集完整测试，交付结果不可稳定复现 |
| P0 | 生产 Trace、指标、审计与告警 | 当前缺少完整执行轨迹，线上错误很难定位，也无法计算核心 Agent 指标 |
| P1 | RAG 质量评测与引用链 | 已有检索管线，但缺少检索质量基线、引用完整性和文档版本治理 |
| P1 | 记忆治理 | 已有记忆读写，但仍需冲突、过期、撤销、来源、置信度与用户可见性治理 |
| P1 | 真实基础设施集成与故障演练 | 文档明确说明 MySQL、Milvus、Neo4j、PostgreSQL 尚需真实联调 |
| P1 | 数据安全与上传防护 | 文档上传、OCR、外部检索和多租户场景需要更完整的安全控制 |
| P1 | SLO、容量与降级策略 | 已有 HPA 和超时，但还没有基于业务目标验证容量与降级行为 |
| P2 | 模型与提示词版本治理 | 缺少模型升级、Prompt 变更、Schema 变更与回滚之间的统一版本关系 |
| P2 | 用户反馈闭环 | 缺少将纠错、拒绝和不满意样本沉淀回评测集的机制 |
| P2 | 多 Agent | 当前任务复杂度尚不足以证明必须采用，多 Agent 应后置 |

## 4. P0：上线前必须补齐的技术点

### 4.1 离线评测与黄金数据集

#### 当前缺口

项目曾有评测数据、Evaluation Runner、LLM Judge 和评分模块，但当前工作树显示这些内容已被删除；架构文档也明确说明独立评测子系统已移除。现有测试主要验证代码行为，不能回答以下问题：

- 推荐是否真的满足用户意图；
- 过敏场景的漏拦截率是多少；
- 工具选择、参数构造和执行轨迹是否合理；
- RAG 是否召回正确证据；
- 模型或 Prompt 修改后质量是否退化。

#### 建议实现

建立 `evaluation/`，但不要把它重新做成耦合生产服务的庞大子系统。优先采用离线 Runner：

```text
evaluation/
  datasets/
    safety.jsonl
    intent_and_tools.jsonl
    retrieval.jsonl
    memory.jsonl
    adversarial.jsonl
  rubrics/
  runner.py
  scorers/
  reports/
```

每条样本至少包含：

- 输入消息与必要历史；
- 用户过敏、禁忌和偏好；
- 允许或禁止调用的工具；
- 预期结构化结果；
- 必须包含或不得出现的食材；
- 是否应澄清、拒绝或请求人工审批；
- 检索相关文档 ID；
- 风险级别和评分权重。

#### 首批数据集建议

1. **过敏安全集**：直接过敏、同义词、衍生物、否定句、历史冲突、用户尝试撤销过敏等。
2. **工具路由集**：食谱查询、详情、推荐、生成、知识检索和无需工具的问答。
3. **失败恢复集**：超时、参数错误、空结果、外部 API 失败、重复工具调用。
4. **RAG 集**：问题—相关文档—相关 Chunk—正确引用。
5. **记忆集**：稳定偏好、临时要求、第三方描述、冲突记忆、明确纠正。
6. **对抗集**：提示注入、伪造工具结果、要求忽略过敏约束、越权访问其他租户资料。

#### 核心门槛

- 严重过敏漏拦截率：`0`；
- 不安全食谱发布率：`0`；
- 未知工具调用率：`0`；
- 高风险动作绕过审批率：`0`；
- 工具选择准确率：先建立基线，再设置不可回退阈值；
- 任务完成率、平均工具调用数、P95 延迟和单个成功任务成本：持续记录版本差异。

#### 验收标准

- CI 能用固定模型替身运行确定性评测；
- 夜间任务可调用真实模型运行非确定性评测，每条样本至少重复 3 次；
- Pull Request 显示相对基线的质量变化；
- P0 安全指标下降时禁止合并或发布。

### 4.2 食品安全领域证据与风险模型

#### 当前缺口

当前安全层的优点是：不信任模型自报结果，而是根据结构化食材证据做确定性检查，证据不足时 fail-closed。但现有匹配逻辑仍以规范化字符串、前缀和后缀规则为主，难以完整覆盖：

- 过敏原别名、俗名、商品名和多语言名称；
- 乳清、酪蛋白、花生油等衍生物；
- 复合调味料中的隐藏配料；
- “可能含有”“同一生产线”“共用油锅”等交叉污染风险；
- 食材替代前后的风险变化；
- 来源缺失、来源冲突和证据过期；
- 医疗级个体差异和剂量风险。

#### 建议实现

建立版本化的领域本体和证据模型：

```text
Allergen
  canonical_id
  names[]
  aliases[]
  derived_ingredients[]
  may_contain_relations[]
  cross_contact_rules[]
  jurisdiction
  source
  source_version
  reviewed_at
```

每个食谱证据至少记录：

- 原始食材文本；
- 规范化食材 ID；
- 匹配到的过敏原及匹配规则；
- 信息来源和版本；
- 食材列表是否完整；
- 是否存在交叉污染声明；
- 判定时间和判定器版本。

将风险明确分级：

- `blocked`：明确命中过敏原或禁止食材；
- `needs_clarification`：用户约束不明确；
- `insufficient_evidence`：配料或来源不完整；
- `cross_contact_unknown`：交叉污染无法确认；
- `allowed_with_notice`：只涉及普通偏好，不是安全约束；
- `passed`：在当前证据范围内未发现冲突。

#### 产品文案边界

系统不应宣称“绝对安全”或替代医生建议。面向用户的表述应是：“根据当前可用配料信息，未发现已记录的冲突；加工和交叉接触风险仍需向商家或生产方确认。”

#### 验收标准

- 所有安全决定可追溯到食材、规则、来源和版本；
- 复合配料、衍生物和交叉污染分别有测试集；
- 未知或冲突证据不能被转换成 `safe`；
- 领域规则更新有变更审查和回归报告。

### 4.3 可复现开发环境与 CI 门禁

#### 当前缺口

- `pyproject.toml` 声明 Python `>=3.11,<3.13`，当前直接执行使用的是 Python 3.13。
- 本地环境缺少 `langgraph`、`aiofiles` 和 `argon2` 等项目依赖，测试在收集阶段中止。
- `pyproject.toml` 声明 `README.md`，但仓库当前没有该文件。
- 有 Makefile 验证命令，但尚未看到仓库内 CI 工作流。

#### 建议实现

- 锁定 Python 3.12，并在 `environment.yml`、Dockerfile、CI 和本地说明中保持一致。
- 使用 lock 文件固定直接和传递依赖版本；至少在发布构建中使用哈希校验。
- 新增真正可执行的 `README.md`，说明环境创建、依赖安装、服务启动、迁移和测试。
- CI 顺序建议：
  1. 依赖安装与缓存；
  2. Ruff lint；
  3. Ruff format check；
  4. MyPy；
  5. 单元测试和覆盖率；
  6. 架构约束测试；
  7. 安全评测集；
  8. Docker 构建与镜像扫描；
  9. Kubernetes 清单校验；
  10. 受控的 Testcontainers 集成测试。

#### 验收标准

- 新机器依据 README 可在 15 分钟内完成首次测试；
- CI 不依赖开发者机器上隐式安装的软件包；
- 测试、Lint、类型检查和 P0 评测全部通过才允许合并；
- 发布产物记录 Python、依赖、模型、Prompt 和 Schema 版本。

### 4.4 生产 Trace、指标、审计与告警

#### 当前缺口

项目保留了普通日志、请求 ID、健康检查和运行预算，但独立 Trace、OpenTelemetry、LLMOps、轨迹查询接口已经移除。这降低了运行时复杂度，却也导致线上难以回答：

- 一次请求经过了哪些节点；
- Planner 为什么选择某个工具；
- 工具耗时、失败和重试发生在哪一步；
- 哪类请求最容易耗尽预算；
- 哪个模型、Prompt 或检索版本导致质量回退。

#### 建议实现

恢复“最小可观测闭环”，不需要恢复面向用户的 Trace API：

- 使用 OpenTelemetry Span 表示 Workflow、Agent 节点、模型调用、工具调用和检索调用；
- 使用不可逆散列或内部 ID 关联请求、会话和租户；
- 默认不记录原始 Prompt、回复、过敏信息和文档正文；
- 对调试采样设置严格访问权限、脱敏和保存期限；
- 指标至少包括：
  - 请求成功率和 P50/P95/P99 延迟；
  - 首包延迟与流中断率；
  - 各节点耗时；
  - 工具成功率、超时率、重试率和熔断率；
  - Token、成本和预算耗尽率；
  - 澄清率、拒绝率、人工审批率；
  - 安全拦截率和证据不足率；
  - RAG 无结果率和低置信度率；
  - Checkpoint 恢复成功率。

#### 验收标准

- 可从一个请求 ID 定位到节点、工具和外部依赖耗时；
- 敏感文本默认不进入日志和 Trace；
- P0 安全错误、数据库不可用、检索不可用和预算异常均有告警；
- 仪表盘可按版本比较成功率、延迟和成本。

## 5. P1：进入生产前应补齐的技术点

### 5.1 RAG 质量评测、引用链与版本治理

当前已有较完整的混合检索实现，但“有检索管线”不等于“检索有效”。需要补充：

- Retrieval Dataset：Query、相关文档、相关 Chunk 和难负样本；
- 指标：Recall@K、MRR、nDCG、引用精确率、引用覆盖率；
- 每个回答中的事实与 Chunk ID、文档 ID、页码、版本建立对应关系；
- 入库时保存解析器、Chunker、Embedding 和索引版本；
- 文档替换采用版本化切换，失败时保留旧版本；
- 删除文档时同时删除向量、BM25、原文件和派生数据；
- Prompt Injection 文档检测：文档中的“忽略系统指令”等文字只能作为数据，不能改变 Agent 策略。

验收门槛应按不同文档类型分别建立，不能只用统一的相似度阈值。

### 5.2 记忆治理

当前项目已经区分过敏、禁忌和普通偏好，并避免从临时或第三方表达中直接写入本人长期记忆。下一步应增加：

- `source`：来自用户明确声明、历史推断还是管理员导入；
- `confidence`：推断型记忆的置信度；
- `valid_from`、`expires_at`：临时偏好和过期信息；
- `supersedes`：新记忆替代了哪条旧记录；
- `status`：active、revoked、disputed、expired；
- 用户查看、纠正、撤销和导出自己的记忆；
- 写入幂等、冲突检测和审计记录；
- 过敏记录变更的二次确认或更高等级审批；
- 数据保留周期和“被遗忘”流程。

不要使用“让模型自由总结后覆盖旧记忆”的方式更新安全关键资料。

### 5.3 真实基础设施联调与故障演练

当前文档明确说明生产 MySQL、Neo4j、Milvus 和 PostgreSQL Checkpoint 尚需环境验证。建议建立两层集成测试：

#### PR 层

- 使用 Testcontainers 启动 MySQL、Redis；
- 对迁移、事务、身份隔离、队列和幂等进行验证；
- 对 Milvus、Neo4j 和 PostgreSQL 选取关键冒烟测试。

#### 预发布层

- 使用与生产相同版本的托管或集群服务；
- 验证多 API 副本同时恢复 Checkpoint；
- 验证 Worker 重启、重复消费和毒任务隔离；
- 模拟 Milvus、Neo4j、Redis、外部食谱 API 和模型服务分别不可用；
- 验证超时、降级、重试、熔断与恢复后数据一致性。

特别要验证 BM25 SQLite 文件在 RWX 存储、多 Worker 并发替换时的锁和一致性。如果并发写入不可控，应迁移到共享搜索服务，而不是依赖文件共享。

### 5.4 数据安全与上传防护

需要补齐的上传与知识库安全点：

- 不只依据扩展名，校验 MIME 和文件魔数；
- 限制 PDF 页数、图片像素、压缩展开大小和解析耗时；
- 防止 Zip Bomb、路径穿越和恶意嵌入对象；
- 可选恶意软件扫描；
- 上传对象使用不可预测 ID，存储路径不得使用用户文件名；
- 所有文档查询、删除和下载都强制 Tenant 过滤；
- 对 OCR 和解析进程进行资源隔离；
- 外部 URL 获取防止 SSRF，限制域名、协议、重定向和响应大小；
- 敏感文档加密、设置生命周期并支持彻底删除；
- 日志中不记录令牌、密码、完整健康信息和原始文档内容。

### 5.5 SLO、容量测试与降级策略

HPA 当前主要按 CPU 扩缩容，但 Agent 系统的瓶颈通常是模型并发、外部 API、数据库连接、队列长度和 Token 配额。建议定义：

- 可用性 SLO；
- P95 首包时间和总响应时间；
- 每分钟成功任务数；
- 每个成功任务的成本上限；
- 入库队列等待时间；
- 安全复核超时策略；
- 模型、Reranker、Milvus、Neo4j 和外部食谱 API 的依赖预算。

降级顺序建议：

1. 关闭非必要 Rerank；
2. 降低召回数量但保留安全证据完整性；
3. 外部食谱源不可用时只返回本地可核验结果；
4. 模型不可用时提供确定性查询或明确失败；
5. 安全证据服务不可用时停止具体推荐，不能降级为未经复核的生成答案。

容量测试至少覆盖并发聊天、SSE 长连接、文件上传、异步入库和审批恢复。

## 6. P2：持续演进技术点

### 6.1 模型、Prompt、工具和 Schema 版本治理

一次 Agent 发布不只是代码版本，还应绑定：

```text
release_id
code_commit
model_provider/model_name/model_revision
prompt_version
tool_catalog_version
schema_version
retrieval_index_version
safety_rules_version
evaluation_dataset_version
```

所有离线报告和线上 Trace 都记录这组版本，使问题可以复现和回滚。模型升级必须先跑完整黄金集，不能仅凭主观对话体验发布。

### 6.2 用户反馈闭环

增加结构化反馈，而不仅是“点赞/点踩”：

- 食谱不符合偏好；
- 含禁忌或过敏食材；
- 引用不正确；
- 没有回答问题；
- 工具执行失败；
- 记忆错误；
- 其他说明。

高风险反馈自动进入人工复核队列。确认后的典型失败样本脱敏并加入黄金集，形成：

`线上失败 → 人工归因 → 新增评测样本 → 修复 → 回归验证 → 灰度发布`。

### 6.3 多 Agent 是否需要？

目前不建议为了架构完整而改成多 Agent。现有单 Agent 已有清晰节点和工具边界，多 Agent 会增加通信、状态一致性、成本和调试复杂度。

只有满足以下条件之一时再考虑：

- 工具数量增长后，路由准确率经过评测确认明显下降；
- 食品安全审查需要独立权限域和独立发布周期；
- 文档研究任务与食谱执行任务存在完全不同的上下文和模型需求；
- 单次任务需要多个互不依赖、耗时较长的研究分支并行执行。

即使拆分，最终食品安全裁决仍应由确定性策略和独立出口复核负责，不能交给多个模型投票决定。

## 7. 推荐实施路线图

### 阶段 A：建立可信基线

1. 固定 Python 3.12 和依赖锁文件。
2. 补 README 与 CI，确保全部现有测试可复现运行。
3. 建立首批 100～200 条黄金样本，其中安全样本优先。
4. 恢复最小离线 Evaluation Runner。
5. 为每次评测记录代码、模型、Prompt、工具和规则版本。

**完成标志**：任何代码或模型变化都能回答“质量提高了还是下降了”。

### 阶段 B：补齐安全与可追溯性

1. 建立过敏原本体、衍生物和交叉污染规则。
2. 为每个安全决定保存证据来源、版本和规则 ID。
3. 补充结构化 Trace、指标、审计和告警。
4. 增加文档提示注入、租户越权和上传攻击测试。

**完成标志**：任一推荐都能解释“为什么推荐、用了什么证据、经过哪些检查”。

### 阶段 C：验证生产韧性

1. 跑真实 MySQL、Redis、Milvus、Neo4j、PostgreSQL Checkpoint 集成测试。
2. 进行依赖故障、重启、重复消费和多副本恢复演练。
3. 建立负载模型、SLO 和降级矩阵。
4. 用预发布流量验证仪表盘和告警。

**完成标志**：能说明系统在高峰、依赖故障和进程重启时如何表现，而不是只证明正常路径可用。

### 阶段 D：持续优化

1. 建立用户反馈闭环。
2. 评测 Prompt、模型、Rerank 和 Chunk 策略的效果与成本。
3. 根据真实指标决定是否拆分多 Agent。

**完成标志**：每次优化都有数据依据，并能安全回滚。

## 8. 最终建议

SafeMealAgent 现在不缺“Agent 的形状”，而缺“Agent 的证据”。下一阶段不应优先增加更多节点、工具或框架，而应优先完成以下四件事：

1. 用黄金数据集证明它答得对；
2. 用食品安全证据模型证明它拦得住；
3. 用 Trace 和指标证明它出了问题能定位；
4. 用 CI、集成测试和故障演练证明它能稳定运行。

完成这四项后，整理版学习文档中的多数概念才真正转化为 SafeMealAgent 的工程能力。
